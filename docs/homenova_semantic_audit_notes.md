# HomeNova 语义链路只读审计

2026-10-30。本文是开发审计资料，不是运行知识，不应加载到 Skill、提示词或检索源。本次只读代码与已保存真实记录，没有修改业务代码、业务 Skill、原始数据，也没有调用模型。

## 结论

目前的核心问题已经从“SQL 能否执行”转为“执行出的列究竟代表什么，以及它能支持多强的结论”。结构化输出解决格式稳定性，不能替代这条语义链。

最小改进不是再增加一层审核模型或未知指标禁令，而是复用已有 `measurement_requests`、`task_local_measurements` 和 `column_metadata`，将**指标身份、定义版本、实际输出列、适用集合**贯穿生成、执行、证据、计算和报告。代码保留能证明的事实与未确认项；现有最终 Reviewer 针对关键未确认项作判断。

两个真实任务均 `completed` 且 `final_reviewed=true`，但独立业务验收未通过。这是业务正确性缺陷，不能因 SQL 成功或状态完成而降格为展示问题。这里不据此宣称所有数字都错。

## 当前实现：已改善什么，尚缺什么

1. **任务内定义已开始传到证据。** 当前 `sql_batch.py` 合并完整 candidate 给 `_query`；`react_harness.py` 将 `local_measurements` 交给 SQL 模块；`sql_module.py:290–297` 保存到 `validation.task_local_measurements`。这修复了场景1中“候选有、证据无”的传输缺口。场景2 R3/R6已能看到该字段，证明链路改善真实存在，但不能反推更早的场景1已正确。
2. **仍未把任务内定义绑定到实际列。** `output_measurements()` 仅遍历登记指标；`sql_module.py` 先生成登记列元信息，再把任务内定义作为独立数组保存。两份资料同时存在，尚不等于列名与定义逐项对应。R6可作为缺陷回放。
3. **存在修复后继承旧定义的风险。** `_query` 当前仅在 `request.get('local_measurements')` 为真时更新 action；修复候选未给或给空数组时，旧定义可能继续留在同一 action。应保存每次候选自己的定义快照，不能将旧定义自动视作新 SQL 的说明。这是代码路径风险，不是已经证实的当次错误。
4. **登记身份主要靠模型写出的名称。** `query_contract.py:275` 按 `metric.name` 找登记信息；未知单字段量会在317–321行改成物理字段名及字段说明。这有助于避免冒充登记指标，但会丢掉任务内业务身份。未知派生量允许执行并保留 pending 是合理的；问题是后续未逐项处理 pending 就把它用于主要结论。
5. **压缩已补回主要风险字段。** 当前 `compact_metric` 和 `measurement_card` 已保留 `duplicate_risks`、`as_of_policy`，应保留这次修复。仍需检查分量级 `component_policies` 的选择字段：其压缩只保留定义、谓词、成熟度、单位、粒度、cohort及时间，不自动保留分量独有的去重键、风险和观察截点。只有真实元数据含这些字段时才需要补齐，不应虚构。
6. **草稿和Reviewer看到的定义详略不同。** `_context(closing=True)` 给草稿的登记信息只保留定义、单位等少量字段；Reviewer保留更完整的定义和SQL。分角色压缩可以保留，但会改变解读的 cohort、event_time、as_of_policy、必要风险应跟着实际使用的指标卡片，不能仅留在别处等模型自行拼接。
7. **审核结构校验没有证明因果。** `reconcile_review()`能检查问题ID、证据ID、状态及解释层级枚举，不能验证“mechanism”这个选择本身成立。继续由现有Reviewer判断业务强度是合理分工，但它必须核对实际定义与反证，不能把主Agent已写的解释当作审核依据。

## 可实施的最小改进

### 1. 保留一个指标身份，分开存物理来源

沿用当前业务请求与SQL输出，不再要求模型手填机械契约。请求已解析到的正式指标保留登记ID；未知量保留任务内ID。物理字段名放 `source_fields`，不要用它覆盖业务ID。显示名、输出别名允许不同。

在现有 `column_metadata[实际列]` 中记录以下最小绑定，而非另建一套永久指标注册表：

| 项 | 来源与作用 |
| --- | --- |
| `measurement_id` / `kind` | 登记ID或任务内ID；区分 `registered`、`task_local`、`field_measure`。名称不自动决定已验证状态。 |
| `measurement_version` | 登记版本，或任务内定义内容的指纹。定义改变时可识别受影响的证据及计算。 |
| `definition` 与 `unit` | 登记资料复用；任务内量同一次SQL响应明确一次。不要求重复抄写整份登记定义。 |
| `scope` | 复用请求及服务器绑定的期间、对象；指标的事件时间、cohort、分子分母等影响意义的部分必须可追溯。 |
| `binding_basis` | 精确输出映射、已有AST血缘或仅模型声明，明确“知道含义来自哪里”，不把映射当口径正确证明。 |

优先从已有登记匹配、真实SQL输出与AST绑定取得列映射。无法唯一确认时，允许SQL候选额外指明实际 `output_columns`，只核对这些列确实存在；不要让模型再写一份表、筛选和时间 JSON。不要仅凭“来源相同”把新量强行绑定到登记指标，因为相同字段可以构造不同统计集合。

### 2. 未知量允许查，不能无定义地升级为业务事实

- 直接字段展示、探索查询继续可执行；无法绑定的列标为未确认，保留真实结果。
- 有明确任务内定义的量可用于分析，注明定义与边界，不因未登记一律失败。
- 查询到有效数据但核心指标定义尚不清楚时，给主Agent结构化缺口；在已有动作中补定义、改解释或补查，无需新审核模型。
- 若只是补充/纠正已有结果的语义说明，SQL和数据未改变，就维护有版本的注释，不为修一行定义重跑SQL。若实际SQL集合有误，再受控修复、使受影响依赖失效。
- 已解析为登记指标的需求，模型使用其他名称计算不同集合时，应作为“请求与候选含义存在差异”呈现，不能默默跳过登记语义。只有能证明的冲突才拦执行；其余保留具体待核对项。

### 3. 一份定义快照随结果走

每个成功候选的登记绑定与任务内定义，以该候选实际内容形成快照，写入现有结果/证据；修复候选不继承未声明的旧定义。后续计算、结果读取、DataQa与Reviewer都消费同一份列元信息。

上下文压缩按指标ID去重：定义保存一份，证据列只引用ID及版本。当前证据需要的事件、集合、观察截点和去重风险保留；不要求每轮重查全库。任务内定义只归当前任务，不自动成为永久经营规律。

### 4. 最终审核核对“用来下结论的列”，而非所有pending一票否决

将已有 pending 按证据ID与相关指标ID交给Reviewer。Reviewer对报告实际使用的关键未确认项，说明是已核对、需修复、限制解释强度还是与本结论无关；沿用当前一次最终审核及已有Controller修复分支。

先核对指标实际含义，再核对结论层级：成交均价变化可写“成交价格与结构共同变化”；只有进一步证据支持时才写同商品调价及其影响。库存时长需确认期初、实体分区和期间交集；这些是通用状态重建方法，不写成某道题的答案。正常、抵消及未核实方向进入报告核查表，但不要求穷尽全部可能原因或必须找到唯一根因。

不建议“所有pending均禁止完成”。展示换算、辅助维度等局部不确定性可以有边界交付；会改变主要指标、用户范围或核心解释的缺口，应继续补查或明确部分完成。`complete`表示已在合理边界回答用户问题，不能靠模型把 `metric_scope_matches=true` 填好就获得。

## 验证建议：先验证贯穿，不用付费反复猜

先用已保存产物做离线回放：

1. R3/R4任务内漏斗定义从candidate到action、validation、evidence、草稿/审核上下文完整保留；修复给空定义时旧定义不复活。
2. `paid_goods_quantity`业务身份不被字段 `quantity` 替换；登记量、任务内量、原始字段量各自能绑定真实列。
3. R6的两个未定义派生列形成可见语义缺口；补充定义不产生SQL调用。未登记的合法比率仍能查，不一律fail。
4. 改变输出别名不改变登记定义版本；改变事件集合或cohort会改变任务内定义版本；跨期计算继承真实单位和口径。
5. 上下文压缩保留实际使用指标的风险与观察截点，且不重复叠加；无关指标不注入。
6. 最终审核能保留事实/分解结论，同时指出库存时长错误和调价机制证据不足；同稿同证据不重复审核。

离线链路通过后再进行少量真实全流程验收，沿用已有独立核算判据。SQL与HTTP成功、模型自评完成以及结构化Schema通过均不得代替业务验收。

## V2参考的适用边界

已只读检查桌面V2的 `single_database_agent.py` 与 `data_qa_agent.py`。可借鉴的是：查询角色只负责取数、真实数据库错误反馈用于原目标修复、报告和图表引用真实来源列。V2的DataQa主要核对来源、列及展示工具，它本身没有证明多步骤经营因果或库存状态重建的机制。因此“V2查数体验好”可以作为复用底层查询组织的理由，不能作为取消语义贯穿或认定报告可靠的证据。
