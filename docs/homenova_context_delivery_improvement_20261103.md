- 主 Agent 接收当前有效判断、完整检查目录和精简结果视图。旧大表默认只保留引用；最近结果和小结果提供必要行，明细按需读取。结果的范围、单位、完整性、未核对项仍保留，正常项和反证不因无异常而删除。
- 同一判断使用稳定 ID 更新；撤回、失效、替代记录保留在历史中，不继续当作当前判断发送。支持与反驳的状态只是调查判断，不是证据认证。
- SQL 重试重新组装当前待处理项所需资料和依赖；已完成同批查询不继续占用修复输入。业务协议中去掉重复的任务头、已确认条件和规范化请求副本；旧单查询链路仍保留唯一的已确认条件。
- 报告 Agent 接收实际证据、相关正常检查和调查判断；核对后形成当前结论。修订时收到上一稿与具体审核意见。审核仍在交付前执行，不每轮触发，也不代替报告 Agent 改写正文。
- 短引用由程序准确绑定完整 ID；存在同名短 ID 时不能自动绑定。未知引用进入一次定点修复，携带错误和前稿；不猜配错误任务前缀。重复的相同报告请求不再次调用模型。
- 八轮只限制新增取证。保留收尾决策、必要沟通和报告整理；调查不完整但正文可靠，可以交付阶段报告。没有可靠审核稿时保留进展，不用程序表格拼报告。
- “生成报告”“根据刚刚的结果”等明确续作优先寻找同会话、同用户、同数据源的既有调查结果，越过误建的空澄清任务；恢复原任务及原预算，直接进入报告流程。
- 入口必要问题先持久化并等待回答，不启动主 Agent 调查。提问卡片包含问题、原因、回答区域和提交按钮；调查中的可选背景问题允许跳过。跳过保留未知，不形成默认答案；用户口述也不自动成为因果证据。
- 查看表和字段使用授权元数据读取路径。内部缺字段先补查资料，不让用户解决 SQL 实现问题。
- 页面区分工具执行成功、调查结束和报告交付。无报告时不显示“已交付当前分析”，不把失败提示另建成经营报告；已恢复查询的问题卡更新为已解决。技术停止原因保留在详情。

## 真实测试后补修，只有离线验证

1. 审核协议显式声明 `repair_scope`。仅报告文字、换算、引用或展示错误，直接交报告 Agent，避免再绕回主 Agent；即使审核 action 写成 partial，但仍明确要求报告修复，也走该路径。正确证据不因文案错误而失效。
2. 三个角色统一强调：“主因／主导因素”也是因果强度判断，不能加一句“高度相关”就放行；用户口述与同现关系不能升级为机制证据。
3. 前稿只传正文和图表定义，去掉其重复的完整数据表。数字阅读视图改为列名加二维行数组，所有原值、单位和逐组计算均保留。对这次真实首稿输入离线验证：该视图 59,747 → 31,569 字符，减少 47.2%，还原后逐单元格完全一致；没有为比较调用模型。
4. 查询历史错误在成功后更新为已解决；同一核心缺口固定阶段标识，不再跨阶段复制提示。已撤回的事实禁止继续作为事实引用。
