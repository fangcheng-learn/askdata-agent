## 1. 核查的任务与结论

任务：**调查2026年7月相较6月的成功支付商品GMV下降。**

保存的任务描述：

> 请调查2026年7月成功支付商品GMV为什么比6月下降：先核实变化，找主要贡献，再检验有证据的解释及反证。金额用欧分，区分贡献、关联与原因。

主要问题是审核与Controller之间的执行契约不完整：审核发现的缺口未必转化为工作；模型建议交付时，代码可能直接结束为部分完成；旧停止原因又可能永久阻止完成。增加审核次数不能解决这些分支问题。

“有缺口且仍有合法、必要、可执行的工作”应继续处理。“部分完成”应表示本轮已经停止并交付可答部分，同时列明无法继续的原因；不能把它当作执行中的进度标签。确实触及步骤修复限制、任务预算或已核实的数据能力边界时，可以部分交付，不应无限继续。

因此，不能把记录概括成“审核总是建议完成，程序总是部分完成”：第3次存在该矛盾；第4次是明确的部分交付；第5、6次的问题是错误放行。

### 第3次为什么本应继续

记录中的过程审核明确指出：S3只查7月，需要补6月同维度数据，`issue_type=evidence_gap`，受影响步骤为S3。

停止时主动处理128.569秒，按调查240秒计算，还剩约111.431秒调查时间；工具仅用6／20次，S3额外修复仅用1／2次，重规划用0／1次。总预算还剩171.431秒，其中包含收尾预留，不能全部当成调查时间。

这没有证明下一次查询一定成功，但足以排除“程序记录显示所有相关预算均耗尽”的解释。应在同一任务内尝试修复S3，或在确实遗漏计划方向时使用重规划额度。最终审核声称修复耗尽，与程序预算不一致，不能作为合法停止依据。

当前代码已在较早修复中补入“`continue`＋无待执行步骤＋仍有未答项→修复或重规划”的回退。前次定位用第3次过程审核输入检查Controller，确实会把S3标回待执行。这只是旧机制的控制分支验证，尚未证明真实补查和最终交付成功，也不代表本次分工已实施。

### 第4次为什么可以停止

S3发生无效JSON并耗尽2次额外修复。单步限制与任务总时间是不同约束：还有总时间，不代表可以继续尝试同一个失败步骤。应保留总体与贡献结果，说明解释检验未完成；其他独立必要步骤若仍可执行，应先完成它们。

不能通过新建任务、换步骤编号或把同一修复改称重规划来重置额度。

## 4. 已确认的修正方案（实现／验证状态见最新报告）

### A. Executor前置决策、步骤代码校验与Controller调度

保留Planner、Executor、独立最终Reviewer和代码Controller。执行阶段不再通过大模型过程审核决定是否继续；也不增加异常触发的大模型过程审核。

1. 在现有入口同次预处理中形成有编号的具体交付要求，保留完整原始请求。对本例至少分别跟踪“变化核实”“主要贡献”“必要的解释检验及反证”。计划步骤声明覆盖哪些要求；最终Reviewer引用要求编号及真实证据编号。
2. Planner声明步骤目标、依赖、预期输出、前置／不适用条件及其影响范围。例如“若同口径完整结果显示没有下降，则后续下降归因不适用”。这些条件供Executor结合结果理解；V1不要求将任意业务条件编译为通用规则语言，也不让Controller自行解释自由文本。
3. 步骤被调度前，代码先检查权限、剩余预算和依赖可用性。条件不允许时直接走修复、等待或停止等分支，不为了决定动作再调用模型。程序将任务原文、本步目标、已确认时间与口径、相关要求／条件，以及所需真实上游结果传给Executor。S2声明依赖S1时，收到S1结果R1的必要结构化字段及来源，不只收到“上一步已完成”的摘要。
4. Executor在原本用于生成本步SQL或执行分析的同一次模型调用中，先判断本步是否适用。适用时在该调用中继续输出原有查询动作、SQL及查询契约，或本步分析产物；不适用或无法判断时输出结构化建议，不再为该步生成和执行无意义的SQL。不新增“S2前先问模型判断、再问一次模型写SQL”的调用层。
5. 前置判断仅限本步是否执行、是否命中Planner声明的前提／不适用条件、是否需要澄清或重规划。不得逐步重审整个任务的正确性、完整性、因果强度，不把独立过程Reviewer换名迁入Executor。
6. Controller校验建议字段、结果引用、条件及影响范围，核对剩余必要目标、当前任务状态、权限和实际预算，再决定执行本步、跳过相关步骤、定向修复、重规划、澄清或转入交付。GMV大小比较等可确定计算用代码低成本复核；不依赖模型自行宣称“所有工作已完成”或“额度已耗尽”。
7. 每个实际执行步骤完成后，仍进行确定性代码校验：SQL执行状态、查询契约、输入输出字段、已注册指标口径及时间／单位／聚合约束、结果完整性和步骤依赖。保存真实结果编号、数据、校验项和错误，再传给依赖步骤。模型在查询前作出的建议不能证明尚未返回的本步结果正确。
8. 最后一步没有下一位Executor读取其新结果，由代码完成必要检查，已有草稿生成和独立最终Reviewer承接其结果分析与交付检查，不新增一次末步过程审核。必要工作完成或确有依据需要有边界收尾时生成草稿；最终Reviewer发现可处理缺口时仍交回Controller，不直接降为partial结束。

#### 前置决策的结构化输出

输出至少覆盖以下语义；具体字段命名可在实施时细化，不改变职责：

| 字段 | 含义及约束 |
|---|---|
| `action` | 执行本步、建议跳过、请求澄清、请求重规划或请求交付；这是建议，不直接设置任务终态 |
| `premise_status` | 已确认、已推翻、尚不能判断；数据缺失、不可比时不能写已推翻 |
| `condition_id` | 对应Planner声明的条件；不能临时编造一个条件来缩小用户任务 |
| `evidence_ids` | 真实上游结果引用；引用用户、任务及快照范围须合法，必要时携带可复核比较值 |
| `affected_requirement_ids`及影响步骤／分支 | 哪些要求不适用或受阻；跳过本步、跳过某分支和整项收尾必须区分 |
| `remaining_requirement_ids` | Executor识别的剩余目标；Controller与服务端完整任务清单核对，不能信任模型返回空数组就结束 |
| `reason` | 简短事实依据及建议动作原因，不要求输出长篇思考过程 |

“命中条件立即停止思考”在方案中转为可检查行为：停止扩展该步调查、停止生成／执行该步SQL，立即返回动作字段；不承诺控制或观测模型内部何时停止思考。权限、预算、依赖及SQL错误由代码当场处理，不等待下一步模型来发现。

#### GMV没有下降时的完整后续路径

以“8月GMV为什么比7月下降”为例，S1真实查询在绑定快照、同口径和完整比较期下显示8月GMV高于7月。S2在已有单步调用中读取R1，报告下降前提被推翻、引用R1、指出仅下降归因相关要求不适用，并列出仍需完成的其他目标；不生成下降贡献SQL。

Controller先复核时间、范围、口径、完整性和大小比较，再按原任务处理：

| 原任务与数据状态 | 后续动作及交付要求 |
|---|---|
| 只要求解释整体下降，实际没有下降 | 将下降归因及相关解释要求标为不适用，保留前提核实结果；生成包含两期数字、变化和纠正说明的草稿，最终审核后可正常completed，不因前提被推翻自动partial |
| 另有明确的独立目标，如排查品类风险 | 只跳过不适用分支，保留独立目标并继续执行；全部必要目标完成或有依据不适用后再交付 |
| 比较期缺失、数据不完整或口径不一致 | 标为尚不能判断，按实际缺口修复、补查或必要澄清；不能把无法判断当成没有下降 |

不自动改题去调查增长原因，不切换时间／范围／口径或挑选局部下降来迎合原假设，也不把停止下降归因等同于立即结束整个请求。若原任务另含相关独立目标，只按已声明目标继续。

| 当前事实 | 必须采取的动作 |
|---|---|
| 有缺口，原计划有可执行步骤 | 执行该步骤 |
| 有缺口，关联步骤可修复且额度未耗尽 | 定向修复，保留独立结果 |
| 有缺口，需补充计划且重规划额度可用 | 回Planner补计划，继承任务和预算 |
| 缺必要用户条件 | 等待补充，暂停主动计时 |
| 已核实能力不支持，或相关预算／修复耗尽，且没有其他可执行必要工作 | 审核可答部分并停止，明确未完成项及原因 |
| 必要要求均已满足或有依据地不适用 | 生成草稿并进行交付审核 |

完成清单只能帮助结构化核查，不能自动证明业务解释正确。代码校验覆盖可确定的两期可比、单位、契约和聚合完整性等约束；独立最终Reviewer检查实际交付文字的正确性、完整性和证据强度。“没有证明唯一根因”并不必然意味着未完成；“根本没有检验必要解释”也不能包装成能力不足。

异常优先使用现有代码分支和受控状态处理。Executor无法据现有证据判断本步适用性时，应明确未决问题和所需数据，建议补查、澄清或重规划，不把判断不出当作终止证明，也不临时追加过程Reviewer。未来确需独立的复杂业务过程审核时再另行评估，不纳入当前V1。

### B. 拆开历史事件、局部阻塞和任务停止

- 历史事件保留用于追溯；当前阻塞单独记录作用范围、关联要求和步骤，修复后依据新证据关闭。
- S1修复耗尽只阻塞S1及其依赖；独立S2的修复资格由S2自身预算与任务剩余预算决定。
- 最终状态根据当前未完成要求、有效证据、审核状态和有效停止条件统一推导，不再由任意非空历史字符串永久否决完成。
- 部分交付必须有程序核验的停止依据。模型不能自行宣称时间、工具或修复额度耗尽，也不能仅用“暂未查询”证明能力不支持。

保持现有对外状态兼容，增加明确的停止原因与未完成项；界面分别显示：

- `completed`：必要要求完成或有依据地不适用，且交付审核通过。
- `partial`＋已审核：已停止并交付可靠部分，列明无法继续的原因。
- `partial`＋审核未完成：已停止，仅保留结构化结果供核对，不展示未审核草稿为结论。
- `waiting_clarification`：当前任务等待用户补条件，回复后继承任务和剩余预算。
- `failed`：无法交付可靠业务结果，列明失败类别。

仍在执行时使用内部执行阶段表达进度，不提前发送终态partial。预算或能力限制导致的终态partial不自动重新建任务继续。

### C. V1审核调用调度：执行阶段零过程审核，正常交付一次最终审核

- S1、S2、S3等中间执行步骤完成后，运行必要的代码校验和Controller调度，不调用独立大模型过程审核；依赖它的下一步在原有Executor调用中读取结果并作本步前置决策。前提核实、方向选择、末步检查和异常处理均不能成为新增过程Reviewer的入口。
- Planner声明步骤前置／不适用条件及影响范围，Executor返回结构化建议，Controller校验及执行；不再把“Controller解释任意Planner业务规则”作为V1前置工程。旧实现的`review_after`、`review_reason`不作为新方案审核调度依据；代码中保留兼容字段但不调度过程审核。
- 正常执行路径中，计划任务完成、代码校验满足交付条件后生成报告草稿，由独立Reviewer对草稿和证据进行一次最终交付审核。保留Planner和Reviewer职责独立，不要求使用不同模型。
- Reviewer发现数字、证据或完整性问题时，输出具体要求编号、证据编号、缺口和建议动作，交由Controller结合实际状态和预算处理。存在可执行修复或补查路径时继续工作；确实不能继续时才允许有依据的部分交付或明确的未审核停止。
- 仅当修复／补查带来实质性新证据，或针对审核问题实质修改了草稿，且确有重新审核必要时，才允许再次交付审核。新证据须同步更新受影响的草稿及引用；每次再次审核说明上次未通过项、实际变化及本次审核目的，继续共享原任务预算。
- 没有实质变化的同一份草稿和证据不得再次送审。只换结果ID、版本号、时间戳、排序、空白或格式不构成实质变化；没有进展时由Controller执行受控停止或等待，不通过反复重发同稿争取放行。
- 交付审核以任务要求、范围／口径、实质证据和实际草稿为判定对象。Reviewer在同一次调用中给出的已审核定稿可直接展示，展示层不得再用模型自由改写，也不为排版变化重新送审。
- 各节点按需传递相关口径和完整聚合，保留权限、快照、完整性校验，不把预览当全集。Executor只在原有调用中附带本步适用性判断；即使该步因此不再查询，已有模型调用仍有成本。必要的查询生成、步骤分析和Planner重规划不属于过程审核，也不得借这些名称重新引入逐步Reviewer调度。

三步GMV正常路径示例，每步后保存真实结果并作代码校验，后续Executor前置判断合入本步原有调用：

`S1查询核实 → 保存R1及代码校验 → S2读取R1、判断适用性并生成查询 → Controller校验／执行、保存R2 → S3读取依赖结果、判断适用性并执行 → 代码校验 → 报告草稿 → 独立Reviewer最终审核一次 → 交付`

前提不成立的路径是：`S1保存R1 → S2读取R1返回前提状态、证据、不适用范围与剩余目标 → Controller复核并跳过相关分支 → 继续独立目标，或生成纠正前提的草稿 → 最终审核 → 正常完成`。

审核发现必要缺口时走：

`Reviewer指出问题 → Controller判断可执行路径及预算 → 修复／补查／必要重规划 → 代码校验 → 更新证据和草稿 → 实质变化检查 → 必要时再次最终审核`

步骤数随任务需要确定，正常路径的审核次数标准为0次独立大模型过程审核、1次最终交付审核。前提被推翻且必要要求已完成或有依据不适用时，可以正常完成并经最终审核交付；技术失败或审核预算不足时按受控状态返回，不能为凑次数强制调用Reviewer。历史调用量不能用来承诺固定token降幅。

### D. 界面和过程报告说明“为什么审核、为什么停”

每步显示上游结果引用、Executor前置建议、命中的Planner条件、前提状态、影响范围、剩余目标、代码校验及Controller实际动作／预算约束；明确区分前置决策、代码校验与独立审核。审核事件仅记录最终交付审核及有实质变化后的必要再次审核，显示证据／草稿版本、审核建议、Controller实际处理及再次审核的变化依据。

每个终态显示：已完成要求、未完成要求、停止类别、相关步骤及剩余额度。将“审核建议交付”和“业务任务已完成”分别展示，不再依赖用户从长篇意见中推断。

## 5. 实施顺序与固定验收

实施顺序：先接通Planner的前置／不适用条件与依赖产物、Executor同次调用中的前置决策及结构化建议、步骤代码校验和Controller状态分支，再修订审核调度及无变化重复送审限制，最后调整界面。V1暂缓通用规则解释器。预算不放宽：工具20次、单步额外修复2次、重规划1次、主动300秒／调查240秒、前端等待360秒；内外重试共享额度，澄清等待暂停计时。实施状态与验证结果单独记录，不改变下列通过标准。

在改动前固定以下控制验收，不因失败缩小范围：

| 验收场景 | 修正后应有的行为 |
|---|---|
| 正常三步GMV及其他正常调查 | S1、S2、S3后大模型过程审核调用均为0；生成草稿后独立最终审核1次 |
| 逐步确定性校验 | 每步覆盖SQL状态、查询契约、字段、指标口径、结果完整性和依赖；错误不得被静默放行 |
| 前提判断与方向选择 | Executor在原有调用中读上游数据、判断本步适用性并输出结构化建议，Controller核验及调度；不新增独立判断调用或过程Reviewer |
| 上游结果传递 | S2得到S1的真实结构化结果、引用及口径；数据不从聊天摘要猜测，不只传递步骤成功标记 |
| 同次判断和执行生成 | 本步适用时在同次模型调用生成SQL／契约或分析动作；不拆成“先判断、再另调模型生成SQL” |
| GMV未下降且只有下降归因目标 | 返回前提状态、证据、不适用范围和剩余目标；代码复核后跳过下降归因，经草稿及最终审核正常完成，不自动partial或直接结束请求 |
| GMV未下降但另有独立目标 | 只跳过相关下降分支，保留并继续独立目标；不信任模型返回空剩余清单而漏掉用户要求 |
| 缺比较期、不可比或结果不完整 | 不得标前提已推翻；修复、补查或必要澄清，不用缺数据作停止证据 |
| 终止作用范围与行动边界 | 区分跳过当前步、跳过分支和整项收尾；不生成不适用步骤SQL，不擅自改题调查增长或另找局部下降 |
| Executor结构化建议不合法 | 无效条件、越权／失效结果引用、越界影响范围被代码拦截；预算、依赖失败无需等下一模型发现 |
| 最后一步结果及简单算术 | 最后一步交给代码校验、已有草稿生成和最终审核，不额外补过程审核；GMV比较等明确计算由代码复核 |
| 第3次同类：必要比较期遗漏且仍有额度 | 比较期代码检查、Executor前置判断或最终Reviewer发现缺口后，Controller同任务定向补查；独立结果不重算，不直接终止partial |
| 最终审核建议complete，但有未完成可执行步骤 | 返回执行；不能直接降为partial后结束 |
| 最终审核建议partial，理由只有尚未查询 | 有合法动作及预算则继续，不接受无依据的停止 |
| 必要要求已满足且代码校验通过 | Controller进入草稿及最终审核；不凭队列为空制造停止原因，不额外调用过程审核 |
| S1耗尽，独立S2仍可执行或修复 | S2继续；S1及其依赖受阻，不绕过S1额度 |
| 历史缺口已解决 | 关闭对应当前阻塞，保留事件；最终状态依据当前事实推导 |
| 第4次同类：必要步骤修复2次耗尽 | 不再重试同一失败工作；完成其他独立工作后审核部分交付 |
| 任务预算耗尽且交付审核未完成 | 明确停止并标审核未完成，不展示未审核草稿 |
| 空结果、证据矛盾、前提被推翻、缺条件 | 按代码分支和既定规则修复／补查、重规划、纠正前提、等待或停止；异常触发的大模型过程审核调用为0 |
| 本步适用性或复杂判断无法确认 | 输出尚不能判断、未决问题及所需证据，进入补查／重规划／澄清等受控分支；不擅自收尾，不追加独立过程Reviewer |
| 修复／补查得到实质性新证据并更新草稿 | 记录实际变化，必要时再次最终审核；仍共享原任务及剩余预算 |
| 审核意见导致草稿实质修改 | 必要时再次最终审核修改内容；同次Reviewer输出的已审核定稿直接展示 |
| 草稿和证据没有实质变化，或仅变ID／时间戳／排版 | 不新增Reviewer调用，不反复送审同一份草稿；Controller按状态和预算处理 |
| 审核字段与解释互相矛盾 | 不以空unanswered或整段问题字符串判完成，关联到具体要求与证据 |
| 商品ID传递、证据实质更新、修改时间范围 | 普通参数直接传递；实质证据或范围／口径变更重做相关校验并更新草稿，必要时再最终审核；纯标识变化不触发再审，继续校验用户及快照范围 |

本地控制测试只能验证流程。真实业务验证先安排一条GMV任务，使用真实模型、检索、MCP和数据，独立核算关键数字并检查实际界面。失败后记录结果、回到离线定位，不自动重新发起整条付费任务，不重复十题全量回归来排错。后续用户授权的第二题须与GMV不同，累计最多两次；两次已用完。最初方案阶段新增付费调用为0，不能与后续实施阶段混记。
