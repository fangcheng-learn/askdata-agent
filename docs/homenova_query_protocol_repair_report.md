# 查询协议与业务取证轮次修复

2026-10-29。修改对象：`references/askdata_studio`。本次未新增付费模型调用或真实 Agent 任务；历史三题失败保持，未重写为成功。

## 原因与修复

最近失败任务 `183163c82b72` 使用的是 **ecommerce_ops 演示数据源**。其订单字段检索没有继承任务时间条件，缺少真实的 `ordered_at`；模型写出了不存在的 `order_time`，还添加了数据库前缀。查询契约同时缺少 `time_range.field`，使用了不符合接口的边界键。最先出现的格式错误遮住了后面的 SQL 字段错误，不能把它都归为误拦。

已实现：

1. **继承时间条件检索。** 原始时间表达、当前期间／基准、已确认时间条件进入检索；相关表补充真实时间字段，检查点继续保存原始提取信息。已用实际检索节点和 Schema 构建器验证 `orders.ordered_at` 能进入模型材料。
2. **统一查询技术规则。** 普通查数、ReAct首次生成及技术重写共用内置 `database_query` 规则；ReAct与修复收到由后端实际模型导出的同一契约格式。业务 Skill 仍按需选择，查询技术规则自动提供，不额外调用一个选Skill模型，也不占一次Skill读取工具。每次实际注入记录名称、长度及内容摘要校验值，避免重复注入。
3. **减少重复手写。** 模型声明指标名称、真实来源和聚合；程序从 SQL 补齐能确定的表、分组、简单筛选及时间边界，并绑定任务和数据源。唯一明确的时间字段可补齐，等价边界键可规范化。明确冲突保留报错；复杂或歧义条件仍须明确声明。不会把 `order_time` 猜改为 `ordered_at`，也不会替模型创造业务定义。
4. **分清内部编号与 SQL 名称。** 模型表结构只显示物理名称及必要关系。兼容精确匹配当前授权图的内部表ID，并记录规范化；未知前缀、跨快照或越权来源仍拒绝。
5. **按确认后的业务轮次计数。** 新任务每个 `query` 查询批次计一轮，失败也计，最多5轮。Skill、语义检索、日期、已有结果读取／计算、澄清和交付建议不占取证轮，但仍记录实际模型／工具消耗。每条逻辑SQL最多生成2次，技术重写不另占取证轮。第5批结束后受控收尾。工具20次、主动300秒／调查240秒及权限保护继续有效。Token只观测。旧任务恢复保留历史计数，不返还预算。

前端分别显示业务取证轮数、ReAct动作决策次数及每条SQL生成次数。正常路径没有新增过程审核。
