# 查询校验与澄清恢复修复 V6

日期：2026-10-28。开发验证资料，不进入运行时知识。

## 本次问题

Safari 当前会话使用的是 `ecommerce_ops` 电商演示数据。用户问“2026年六月GMV”，系统询问店铺还是商品，用户选择“店铺维度GMV”后仍被查询契约检查拦截，SQL 未执行。

根因是两处实现缺陷叠加：校验器把不同表的字段描述文字不同当成定义冲突，并要求最初问题包含完整表名；澄清状态虽然已给 Executor，却没有传给校验器。此前 HomeNova SQL 回归没有覆盖这个普通查数的续查分支。

## 实际修改

- 移除按描述文字差异和原文是否包含完整表名判定指标冲突的硬拦。来源未证明时记录 `pending_checks`，不会认证业务正确。
- 同名原始字段的来源澄清选项可提供 `metric_sources`；服务端校验其确属当前授权 Schema，并向用户展示登记来源。用户选择后才记录任务、数据源范围内的绑定，给后续检索、Executor 和校验器使用。SQL 自己声明的来源不算用户确认。
- 已确认店铺来源后，SQL 改用商品来源仍硬拦；跨任务、跨数据源的旧确认不能充当当前依据。旧选项保存真实澄清历史作核对材料，不猜测来源、不要求重新提问。
- 单字段派生、组合筛选、常量日期计算及多个聚合组合等无法由有限规则证明的表达，保留待核对项后执行。直接值冲突、重复条件掩盖冲突、错误时间边界、金额与件数冲突仍拒绝。
- CASE 条件、连接条件不再无提示地认证总体已经过滤；外连接保留侧、分量条件与总体条件不一致等疑问进入最终审核材料。

权限、单条只读、实际表和字段、数据库预编译、快照隔离、结果引用、预算和重试上限保持。没有新增模型过程审核或付费调用。
