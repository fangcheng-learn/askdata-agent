# Harness V1 模型消耗核查

日期：2026-10-27。开发私有评测资料，不得注入运行时模型或检索源。当前已停止新增真实模型测试。

## 结论

消耗过快的首要原因是开发过程中重复执行了六轮全量经营题回归；最重的模型节点是 SQL 生成与查询契约修复，叠加重复发送较大的语义上下文。测试节奏由实施 Agent 控制，此次没有及时收敛到单例修复后再做一次全量验收，是实施过程的问题，不是用户问一次问题就必然需要这样的费用。

## 代码中的放大因素

1. `SingleDatabaseAgent._validated_decision` 每次修正会重发基础Schema、相关指标、工具定义，再附上一版SQL/契约与错误。317次可识别尝试是最大的节点次数来源。
2. `InvestigationHarness._materials` 为规划/审核提供Schema、指标、计划和已有证据；当前仍有重复元信息。历史检索记录中的完整指标JSON中位约10,422字符，最大85,431字符。它们不是token数，Coder还做过紧凑转换，不能把字符数冒充实际账单。
3. 基础查数也通常需要4次Chat：预处理、查询生成、草稿、交付审核；已有结果问答通常3次。多步调查则继续增加执行与阶段审核。
4. 20次工具、2次修复、1次重规划和5分钟限制都针对**每个任务**。它们不是整轮开发的模型调用/token/金额总预算；新测试任务会重新取得预算。六轮回归因此没有被这组限制挡住。
5. 旧客户端没有保存服务端`usage`，也没有显式的输出token上限。此次无法事后精确拆出输入、输出、缓存、思考token到各节点，不应伪造精确归因。

## 已做与仍待做

- 已停止付费复测，没有切换模型、充值、开通服务或修改阿里云配置。
- 已增加任务内按节点记录请求字符量、耗时和服务端数值`usage`的能力。记录不含提示词、密钥或鉴权头；缺少usage时标未知。此次新增记账只通过本地控制测试，真实接口因Arrearage尚未验证。
- 后续恢复应先修一条失败用例，只跑相关单例；单例通过后才安排一次全量回归。不再连续重跑全组来定位同类错误。
- 如继续优化，应减少语义与证据重复、只传当前节点所需材料，并明确设置独立的开发轮次/调用/token/金额预算。新的预算数值和模型选择不在此次核查中擅自改动。
