## 1. 调整目的与已确定方向

当前框架存在两类问题：初始计划在看到业务数据前就确定具体下钻路线；执行和审核虽然完成，仍可能把贡献分布、代理指标或未取证的解释当成充分结论。

本次调整以数据推动下一步调查，采用以下方向：

1. 取消独立 Planner，以及预先生成完整 S1／S2／S3 计划后依次执行的主模式。
2. Flash 只负责意图路由与任务理解：目标、范围、已有信息和待回答问题；**不选择业务 Skill，不安排调查步骤，不生成业务触发条件树。**
3. 原因调查由一个经营ReAct循环读取证据、决定下一业务动作并更新进度；取数经固定独立SQL模块完成，ReAct不直接编写或技术重写SQL。
4. 业务 Skill 提供分析方法、阶段产物、证据要求及结束边界；不固定“店铺→品类→SKU”等路线。
5. 保留代码 Controller、真实结果引用、权限与快照隔离、预算、有限修复、澄清恢复及独立最终交付审核。
6. 简单查数和已有结果问答继续走适合的直接路径，不强制进入长调查。
7. 首版采用单个经营ReAct调查主体及固定SQL模块，不建设动态subagent、子会话或协作调度平台；用户保留后续引入子Agent的方向。SQL模块独立调用模型但共用后端记录，不拥有另一套长期记忆。
8. Token保留估算、实际用量和未知用量记录，不设应用层token硬上限；以最多5轮业务取证、每条逻辑SQL最多生成2次及原工具／时间限制约束执行。准备动作不占取证轮数，仍有真实调用成本。服务重启从已保存检查点继续，次数不重置；不新增付费试跑。
9. 所有数据源的相对时间统一使用机器真实当前日期／时刻为参考，不再以固定快照场景日期代替今天；数据覆盖和授权快照仍独立检查。

这里的 **ReAct 是 Agent 的推理—行动循环，不是 React 前端框架**。现有前端技术栈不在本次调整范围内。

取消独立 Planner 不表示取消目标管理。原问题和未解决问题需要持续保留；改变的是后续动作按证据决定，而不是提前排死。

## 2. 总体流程与职责

```text
用户问题＋相关会话／真实可获取的看板上下文
                         ↓
Flash：意图路由＋明确目标、范围、已有信息、待回答问题
    ├─ 普通交流／必要需求澄清 → 直接处理
    ├─ 简单查数 → 统一SQL模块、结果验证与原回答链路（新模块已接通，真实效果待验收）
    ├─ 已有结果问答／可视化 → 复用合格结果
    └─ 经营原因调查
              ↓
       经营ReAct ← 目标／进度／证据、业务指标定义与能力边界、Skill目录
              ↓
       选择有明确目的的下一动作（可为独立查询批次）
              ↓
       Controller 校验权限、预算、引用及动作参数
              ↓ 查询动作
       固定SQL模块：组装相关完整资料 → 独立SQL生成／受限修复 → 真实MCP
              ↓
       保存真实结果、执行状态和检查结果
              └────────────────────→ 回到同一 ReAct Agent

       证据满足交付要求／需要有边界收尾
              ↓
       同一DataQaAgent生成报告草稿 → 独立最终 Reviewer
                    ├─ 通过 → 展示审核定稿
                    ├─ 有可执行缺口且预算允许 → 返回取证循环
                    └─ 无法补齐／预算停止 → 明确部分完成、失败或未审核状态
```

三条初始路由可沿用现有 `database_query`、`data_qa`、`direct_response`；“需要经营调查”属于任务模式，不要求新增一套入口路由系统。调查中不逐轮重新调用 Flash。

| 部分 | 负责什么 | 边界 |
|---|---|---|
| Flash | 理解本轮目标、对象、期间、比较基准、已有信息和待答问题，选择初始处理路径 | 不选 Skill，不生成业务路线，不把原因请求缩成仅查询环比 |
| ReAct Agent | 按需读取 Skill、理解真实数据、提出候选解释、选择下一动作或交付建议 | 不自行扩大权限、重置预算或把未经核验解释登记成事实 |
| 独立SQL模块 | 接收本轮业务取数要求，准备适用资料、调用SQL模型、校验执行及技术修复 | 不重新路由、不选择业务方向、不逐步生成最终回答；共用任务记录与预算，已接通，真实效果待验收 |
| DataQaAgent | 原data_qa入口分析已有结果，调查收尾直接复用为报告草稿生成器 | 不新开分析循环或长期记忆，不重复路由或额外增加草稿调用；双模式适配已接通 |
| 业务 Skill | 提供分析方法、必要产物、证据标准和结论边界 | 不写入私有答案、固定参考 SQL 或逐题分支 |
| 代码 Controller | 执行工具、维护状态、处理确定性校验、预算、错误及结果有效性 | 不充当解释任意经营条件的规则引擎 |
| 最终 Reviewer | 对照原问题、草稿和实际证据检查正确性、完整性及结论强度 | 正常路径最终审核一次，不恢复逐步过程审核 |

Controller 可以直接处理明确的技术分支，例如权限拒绝、预算耗尽、结果引用失效和确定性计算错误。选择“接下来调查流量还是商品结构”等业务方向，由 ReAct 在已有决策调用中完成，不再增加一个过程判断模型。

## 3. 入口：承接用户的分析起点

### 3.1 Flash 整理的内容

字段名称是工程示意，不冻结为最终 API：

| 信息 | 含义与规则 |
|---|---|
| 原问题／当前目标 | 保留用户原文，明确本轮究竟要解释 GMV、流量还是其他现象 |
| 分析范围 | 全店、站点、指定店铺、品类、SKU、渠道等；当前明确要求优先 |
| 时间与比较基准 | 继承适用的明确条件，不因历史结果不完整而丢掉已知年份 |
| 已有信息 | 标明来自用户描述、会话结果或实际取得的看板结果，并保留来源引用 |
| 待验证解释 | 单独保存用户假设，不能因为用户提出就当成已证实原因 |
| 必须回答的问题 | 忠实整理用户目标，不自动扩写成固定调查步骤或额外经营任务 |

入口不需要完整 Schema，也不猜物理字段。具体查哪些指标，由拿到相关 Schema、指标口径与 Skill 的 ReAct Agent 决定。

### 3.2 三类典型起点

| 用户起点 | 调查从哪里开始 |
|---|---|
| “最近 GMV 为什么下降？” | 在当前全店范围内建立或补齐相关核心指标对比，再判断异常与调查方向 |
| “德国站 Store A 这个月怎么跌得这么严重？” | 继承 Store A 和适用期间，核实该对象变化并查看内部相关指标；不先重做所有店铺排名 |
| “看板说 Store A 流量减少，为什么？” | 直接将 Store A 流量下降的原因作为调查目标；复用看板期间、口径和结果，按需要检查渠道、来源、时段等流量构成，不额外引入 GMV 目标 |

“用户指定了对象”和“用户提出了原因”分开处理：范围可以继承，解释保持可验证、可否定。

“看板说 Store A 流量减少，为什么？”已经明确了待解释现象，应直接进入流量原因调查，不再询问用户是在问流量还是 GMV，也不重新做全盘 GMV 分析。必要的数据核验用于确认流量变化的期间、口径和事实，不改变用户的分析目标。

只有用户原文或实际上下文确实存在会改变答案、且无法消除的关键歧义时才澄清。不得自行添加其他指标或假设，再要求用户解决由系统制造的歧义。

看板上下文必须由系统实际取得并传入；不能假设模型看到了用户屏幕。用户口述的看板发现可以作为线索，不能伪装成系统已执行的查询证据。

### 3.3 “最近”的期间与当前时间

用户已明确：没有说明“最近多久”，且没有可从会话或实际看板继承的有效期间，就先询问，不自行默认最近7天或本月至今。已有明确期间时直接继承，不重复提问；比较基准也优先继承，缺失且会改变答案时一并澄清。

用户已确认：**所有数据源都用机器今天。** “今天／昨天／本月／近N天”等相对时间统一以机器真实当前日期／时刻为参考，按既有明确业务时区解析并标明实际范围；当前时间只提供参考点，不替代“最近多久”的期间澄清。此项明确替代此前 HomeNova 以绑定快照场景日期解释相对时间的产品规则；快照场景日期继续保留为数据元信息，不再充当今天。

时间参考与数据覆盖分别处理：绑定快照、用户权限、交易覆盖、观察截点和完整性约束继续有效。相对时间落到快照未覆盖的日期时，明确说明缺失，必要时请用户选择可查询期间；不能将无记录当零，不能自动退回快照日期、静默缩短期间或换另一截面补数据。可独立回答的已覆盖部分仍按证据边界交付。

例如，真实当前日期为2026-10-29时，“本月”解释为2026年10月；若绑定快照仅覆盖至8月底，就说明无法据此回答10月完整经营情况，不自动改查8月。

首次解析时记录参考时刻、时区和绝对起止边界；同任务后续执行、补其他参数或重启恢复均继承已确定期间，不逐轮重新计算而让范围漂移。用户明确修改期间或提出新的相对时间问题时，再按当前时刻解析并处理受影响结果。

时间解析、相对时间工具及相关 Skill 来源稿和实际应用副本已同步迁移，并通过本地回归。本轮真实业务题使用明确历史期间，不等于所有相对时间边界已通过真实模型验收；历史运行不回写为新规则。

## 4. ReAct：每轮决定下一动作

### 4.1 每轮使用什么信息

经营ReAct读取原目标、当前范围、适用业务Skill、相关指标业务定义与能力边界、已确认事实、候选解释、未解决问题、真实证据及剩余预算。完整物理Schema、SQL规则和具体技术报错由SQL模块按需取得；不要求ReAct自己组织字段检索。

它在同一次调用中形成简短、可记录的行动理由并提出下一动作。查询动作可以包含多个彼此独立的业务取数要求，由固定SQL模块独立调用模型生成SQL；首版可一次首生成调用覆盖整个批次，失败时只重写失败子集。此项显式替代此前“ReAct同次产SQL、不另调SQL模型”的设计，新增调用须单独记账。有结果依赖的查询仍分轮决定，具体规则见第10节及[独立SQL方案](ecommerce_agent_sql_module_and_context_plan.md)。

内部推理不作为面向用户的长篇思维链展示。界面记录行动目的、使用的证据、结果、错误和判断变化。

### 4.2 可用动作

| 动作 | 用途 |
|---|---|
| 读取 Skill | 从应用白名单中取得选中方法正文 |
| 补充语义检索 | SQL模块自动准备本轮必要字段／口径，已有资料充分时复用；ReAct仍可为业务能力缺口提出语义请求，不逐字段安排检索 |
| 读取已有结果 | 按授权引用获取所需列、行或可用聚合 |
| 查询数据 | 提出一个业务取证批次，由独立SQL模块组装资料、生成并通过真实只读MCP执行；每条分别校验、执行、计数及保存；单次数据库执行一条只读语句，见第10节 |
| 确定性计算 | 对真实结果进行日均、变化、贡献、比率等可复核计算；不开放任意系统操作 |
| 请求澄清 | 缺少会改变答案、且现有数据与上下文不能解决的业务条件 |
| 请求交付 | 说明已回答项、证据、未回答项及无法继续的依据，进入草稿与最终审核 |

比较、解释和选择方向可在本轮决策中完成，不另设“纯思考”“观察”或“反思”模型节点。工具返回的真实结构化结果、状态及错误，就是下一轮使用的观察信息。

### 4.3 防止迷失方向

每个动作必须关联一个未解决问题，说明预期取得什么证据。结果回来后更新：

- 新确认了什么事实及其来源。
- 哪些候选解释得到支持、受到反驳或仍无法判断。
- 当前还缺什么，是否值得继续查询。

不要求 ReAct 每轮重写整份计划。允许因证据改变方向，但不得默默更换用户目标、比较期或分析对象来迎合原假设。

例如，用户问 A 店下滑：发现订单下降、访客基本稳定时，可把转化问题列为候选解释，再查同口径证据；不能直接认定转化是根因。需要其他店铺作对照时，查询应服务于解释 A 店，而不是无目的地重新寻找分析对象。

## 5. Skill：写方法与产物，不写死路线

### 5.1 选择和加载

- Flash 不输出所选业务 Skill；ReAct 首先看到白名单中的名称、适用范围和简短说明。
- ReAct 按需请求读取 Skill，Controller 校验白名单后返回正文；后续决策才据正文行动。
- 2026-10-29进一步确认：业务Skill是按需方法，不是SQL许可。复杂调查优先读适用方法；明确的事实核实可先查数，看到结果后再补读。未加载业务Skill不能单独成为查询失败原因；查询技术Skill仍由SQL模块自动提供。
- 不能声称同一次调用先选中了尚未读取的正文，又已经依据该正文完成了查询。
- 不另设选 Skill 模型。选用与读取属于现有 ReAct 循环，实际增加的调用与工具次数如实记录。
- 已加载、版本未变且仍适用的 Skill 可复用；不扫描 docs 或整个仓库寻找知识，不无差别注入全部 Skill。
- `database_query`作为SQL模块内置技术规则自动提供，首次生成与技术修复共用；经营ReAct只按需选择业务方法，不额外选择查询技术Skill。独立SQL模块分工已接通，具体本地验证见本轮实施报告。
- 先接通经营异常诊断；目标分析和库存风险沿用既有兼容能力，不扩展复杂预测或经营操作。

`docs/agent_skills/` 是来源稿，运行时仍须显式注册实际应用副本。文档引用路径不等于已经加载，选择、读取和实际注入分别留痕。

### 5.2 经营诊断 Skill 的必要产物

1. **当前范围的诊断概览。** 优先利用适用结果，补齐与问题直接相关的核心指标；对齐期间、统计集合、单位、粒度及覆盖。指标组随问题变化，不机械要求所有任务查询同一组字段。
2. **有依据的方向选择。** 从实际变化提出候选解释，选择有区分力的取证方向；店铺、渠道、品类、SKU 都可以是候选，不预设固定顺序。
3. **解释验证与边界。** 区分事实、贡献、关联与原因证明；检查关键替代解释及反证，说明哪些问题尚未解决。

月总额对比应注意月份天数、未完整日和可比期间；日均不是所有任务强制使用的口径。订单数、购买用户、购买会话及各类平均金额不得随意互相代理。比率使用相同集合的分子分母，不能平均子组比率冒充总体。

“尚未查询”“查询失败／结果不全”“口径未对账”“确实不支持”应分别表述。字段存在不代表已经具备同口径归因证据，当前没有结果也不代表数据源没有能力。

继续复用现有 Schema、指标和数据源元数据；缺什么补什么，不为本次调整另造独立的“能力注册表”平台。

## 6. 调查记忆、证据持久化与模型上下文

本节已接入独立 SQLite 运行时存储：任务状态、语义材料、动作、预算及结果保存在本地文件，内存作缓存，每轮按需组装模型上下文；JSON／Markdown 用于导出。未增加数据库服务或重建业务数据库。已保存检查点的授权恢复通过本地回归；调用中途无缝恢复、入口首次落盘前的崩溃窗口不在已验证能力内。

### 6.1 任务记录与模型输入分开

任务期间保留完整结果记录、SQL、来源、范围、检查状态和实际依赖；模型每轮只接收当前需要的内容。

| 内容 | 处理方式 |
|---|---|
| 原目标、范围、已确认事实、假设、未解决问题 | 精简、持续更新；关键事实保持结构化并关联真实证据 ID |
| 证据目录 | 列出结果 ID、问题、指标／粒度／期间、列、行数、完整性、版本与可读取内容 |
| 本轮相关数据 | 提供实际需要的列、行或完整聚合；不能只给无法核数的文字摘要 |
| 大表、完整日志、历史失败候选、全部 usage／Skill 事件 | 留在后台供读取与过程报告，不每轮全量注入模型 |
| Schema 与指标口径 | 默认继承已取得且仍适用的资料，缺什么补查什么；按当前动作选取，依第6.5.1节去重，不累计拼接历次检索包 |

例如已有80家店的结果，分析 A 店时可带总体概览、A 店数据及相关对照。重新计算全店贡献时使用完整结果或完整聚合，不能从少量预览推算全集。

### 6.2 可信、完整与失效处理

- 每次实际动作与结果有稳定编号，记录真实输入结果 ID，不依靠聊天摘要猜数。
- 分开标识完整结果、展示预览、截断与结果引用。超过保存上限的结果继续标为不完整，按需要重新聚合或受控读取，不承诺无限保存。
- 读取与复用检查用户、任务、数据源／快照、期间、口径及检查状态；跨任务复用按现有授权机制重新绑定。
- 上游结果修正后生成新版本，关联事实和下游判断同步失效；只重算受影响内容，保留独立有效结果。
- 模型不能把假设写进已确认事实。重复执行旧查询不会自动产生新事实。

任务、预算及完整结果引用现已由独立调查运行时 SQLite 保存，不依赖默认关闭的会话归档开关。进程内缓存清空后，重新校验身份、数据源和快照权限再读取已提交记录。恢复不自动发起付费调查，不把尚未提交或中断未知的调用补记为成功。

### 6.3 成本要求

记录每轮输入量、Chat／Embedding／Rerank 用量、缓存命中、Skill 读取、修复和审核次数。模型上下文只携带必要预算计数与剩余时间，不将完整计费流水、重复日志和所有历史证据倒灌给草稿及审核。

**当前规则为token观测，不实施应用层token限额。** 不因单次输入估算、Chat累计、检索累计、最大输出或收尾token预留触发停止，也不为满足旧token门槛删去必要口径、证据或行数据。仍按当前动作选择相关上下文和展示行数，保留完整结果读取能力；每轮重新发送材料仍计费，不承诺ReAct必然更省token。

用户已进一步确认按**最多5轮业务取证**计数：一次query查询批次计一轮，不论批内一条或多条独立SQL，也不论成功或失败。选择业务Skill、补查字段／口径、日期解析、读取和计算已有结果、澄清及交付建议不占取证轮数；它们仍是真实模型决策或工具动作，单独累计ReAct决策次数、模型用量和工具次数，受20次工具及主动时间限制。已有资料足够就直接查询，不重复准备。

SQL错误的技术重写使用受限修复调用，仅能修正同一逻辑查询的SQL和契约，不能换目标、扩大范围、选择新方向或追加查询，不另占取证轮。每条逻辑SQL总共最多生成2次，包含首次生成和一次重写；一轮中生成多个独立SQL，每条分别记首次生成。失败或重启不能清零。

入口Flash、报告草稿和独立最终审核不占5轮，均继续记录实际模型调用。5轮取证用完后不再调用下一轮普通ReAct开启新调查，使用已有证据受控收尾；还有必要缺口则按原交付规则返回部分完成或未审核状态，不能将“轮次耗尽”当作问题已回答。5轮不是总SQL、工具或模型调用最多5次，也不构成人民币金额上限。旧任务保留历史计数政策和已消耗轮次，恢复不返还旧次数；新任务使用query_batches计数政策，界面明确区分。

- 调用前仍估算输入并记录估算方法；本地Qwen基础BPE加余量不是闭源模型精确分词。词表或依赖不可用时记录UTF-8估算回退，估计偏大不会因此拦截模型请求。
- 覆盖入口、ReAct、SQL重写、草稿、审核及实际检索模型调用。按API usage分别记录Chat、Embedding和Rerank的真实用量，不把不同接口token视为同价，不将本地估算当作实扣账单。
- 未返回usage或中断调用的消耗保留为未知／估计，与已返回的实际用量分开；不能按零费用宣称无消耗，也不把保守估计伪装为实际消耗。
- 每轮记录Schema／口径、Skill、进度、结果等区块的字符数和token估计。工具20次、主动300秒／调查240秒、前端360秒、权限和只读校验继续有效；最终收尾仍服从剩余主动时间。
- 模型服务自身上下文窗口、输出能力、速率和账户额度是外部约束；遇到服务拒绝如实记录，不关闭安全校验或伪装成功。取消应用层token上限不表示模型服务无限容量。

历史说明：前两次真实任务曾被55,195和48,125的UTF-8输入上界触发旧48,000门槛，后续曾修正单次分词估算；160,000／80,000累计限额、4,096输出、60,000收尾预留均属于本次取消前的政策。原JSON、失败和消耗保持，不按当前规则回填通过。

调查记录更新放在原有 ReAct 调用中完成，不另调摘要／记忆模型。后台已保存材料的选择和拼装不重新调用 Embedding／Rerank；新语义检索、模型显式请求的结果读取仍按真实工具规则计数，不能隐藏在上下文拼装中。每轮重新发送的内容仍计入该次模型输入；文件保存不等于模型自动记得，也不等于免费输入。

### 6.4 保存到哪里、保存什么

首版使用独立应用运行时文件 `references/askdata_studio/backend/data/harness_runtime/state.sqlite3`，与原始业务数据及私有开发评测目录分开。采用 SQLite 事务保存，不改变现有可选会话归档开关，也不将过程报告反向注入运行知识。

不以每任务 JSON 作为唯一权威记录，避免任务进度、预算和结果分别写文件时出现不一致。SQLite 本身是本地磁盘文件，可以保存结构化 JSON 字段；需要用户阅读时再导出 Markdown／JSON 报告，导出件不反向成为运行知识。

最少保存四组记录，具体表名由实施确定：

| 记录 | 保存内容 |
|---|---|
| 任务与调查进度 | 任务／会话／用户、绑定数据源和快照；机器参考时刻、业务时区及已解析的绝对期间，快照场景日期作为元信息；原目标及范围；事实、假设、缺口及各自证据版本；澄清状态、草稿、审核定稿及状态；累计主动时长、工具／修复／模型用量与必要预留 |
| 本任务已取得的语义材料 | 相关 Schema 片段、指标定义、来源和语义版本；所选 Skill 的 ID／版本及实际加载记录。只保存实际授权取得的材料，不复制整个知识库 |
| 动作和调用记录 | 稳定逻辑动作 ID、实际尝试 ID、目的、SQL／参数、输入引用、执行前后状态、错误、检查结果及真实用量。记录行动理由和结构化输出，不要求展示内部思维链 |
| 结果索引与结果数据 | 结果 ID、所有者、任务、数据源／快照、语义版本、SQL、列及类型、实际行数、完整性、检查状态与依赖；结果行在同一 SQLite 中分块保存，支持原结果引用分页读取 |

运行内存只缓存当前活跃记录；缓存清空后从 SQLite 读取，不丢失任务依据。结果读取继续校验用户、任务、数据源和快照，不能让模型通过提供文件路径直接读磁盘。

保存上限沿用当前单结果最多50,000行、展示预览200行和受控读取最多1,000行／页。超过上限仍标不完整，总行数未知就保持未知；总体分析优先重新查询完整聚合，不拿保存片段计算全集。持久化不会自动扩大上限。总磁盘容量需要可配置；写入失败或容量不足时明确返回存储错误，停止发起后续动作，保留此前已提交记录，不能把仅内存结果宣称成已持久保存。本方案不新增自动删除业务数据或活动任务的行为。

本轮单结果保存、预览、分页及写入失败停止已接入；总容量控制的实际实现与验证边界见交付报告，不将SQLite内部页和WAL开销视作严格字节级配额承诺。

### 6.5 每轮怎样读、怎样更新

```text
SQLite 中的任务、语义材料和证据
        ↓ 后端选择当前必要内容
原目标＋当前进度＋相关口径／字段＋本轮所需真实数据
        ↓ 同一次 ReAct 决策
进度更新＋下一动作／交付建议
        ↓ 代码保存更新，执行获准动作
真实结果与执行状态写入 SQLite → 下一轮
```

1. **持续提供目标和当前进度。** 原问题、范围、期间与比较基准、用户已有发现及来源、精简事实／假设／缺口持续保留。被否定解释保留简短理由和证据，不每轮倒入全部历史。
2. **只带当前相关语义。** 正在查询或解释的指标定义、必要表字段和关联关系进入上下文；其他已取得材料留在后台，需要时取回。核心定义不能压缩成仅有指标名，已知筛选、单位和统计集合不能为节省 token 而丢失。复用须匹配本任务授权、快照和语义版本；默认继承与补查规则见第6.5.1节。
3. **判断需要数值时提供数值。** “订单基本稳定”等进度描述不能替代两期实际订单数、GMV、变化和口径。本轮相关行／聚合来自真实结果；大表按需读取，不能只给结果编号又要求模型猜内容。
4. **不新增摘要节点。** 工具返回后先保存真实结果；下一次原有 ReAct 调用读取它并更新事实、候选解释和缺口。代码核对引用是否存在、版本与范围是否匹配、数值是否来自引用或已记录计算；不增设一个尝试证明所有经营解释的校验器。模型提出的原因判断不因写进记录就自动成为已验证事实。
5. **版本更新只影响实际依赖。** 每次更新保留任务修订号；同一任务只允许一个有效执行者写入，防止重复点击或并发请求覆盖进度。上游证据或相关语义修正时使受影响内容失效，独立有效结果保留。原始记录保留可追溯，不用新摘要覆盖历史事实。

模型只能通过应用工具读取授权记录，不能自由改任务所有者、证据原始值、权限、预算或审核状态。后端读取和更新已存记录不增加业务模型调用；Markdown 过程报告由这些记录生成，不再调用模型重新编造过程。

#### 6.5.1 Schema 与指标口径：默认继承，按需补查更新

用户已确认并在本轮实现以下策略：同一任务内继承已取得且仍适用的 Schema、指标口径及关联关系，不默认每步重新检索。需要新指标、字段或关系时补查缺口；数据源、授权快照或相关定义版本变化时，重新取得相应资料并检查受影响内容。已通过本地去重、相关性选择和依赖回归；跨部署语义迁移的完整验收仍待完成。

后台维护本任务的“已取得语义资料清单”，复用现有 Schema／指标元数据的稳定编号，不另建独立注册平台，不让模型维护一个智能合并器。代码按如下规则处理：

| 情况 | 处理 |
|---|---|
| 同一编号、同一有效版本再次取得 | 复用已有定义，可补充来源记录；不重复保存或输出完整定义 |
| 取得新编号 | 加入后台清单，后续按需使用；不覆盖整份旧清单 |
| 同一编号出现定义或版本冲突 | 保留旧记录与差异，补取权威定义并核对实际依赖；不静默覆盖，不靠模型把两种口径揉成一种 |
| 检索未命中已有资料或未取得新需求 | 保留仍有效的旧资料，新需求记录为缺口；不能因本轮未命中就删除旧定义或宣称数据源不支持 |
| 授权范围或快照变化 | 按新范围重新取得相关资料，隔离旧材料；不得混用另一个数据截面的定义与证据 |

字段以“数据源＋快照＋表／字段稳定 ID”识别，指标以“数据源＋快照＋登记指标 ID”识别，并另行记录语义版本。不同表的同名字段、不同来源的同名指标不能合并。显示别名依现有元数据映射到稳定编号，不把名称相似当成同一口径；定义冲突也不自动升级为新的 SQL 硬拦截，仍按第7.1节区分明确错误和待核对项。

每轮输入由代码从清单重新选取当前相关内容，同一有效定义在一次请求内只放一份；不把上一轮输入、历次检索包或整份资料清单逐轮叠加。经营ReAct与SQL模型使用不同输入视图但共用一份记录，具体见[独立SQL方案第5、6节](ecommerce_agent_sql_module_and_context_plan.md)。必要样例／取值／单位／覆盖与完整中间关联路径必须保留，不能只删除检索副本或只保留两端表。调查进度和证据通过语义ID／版本引用公共定义，保留查询特有口径；早期关键证据按实际依赖取回，不仅按最近两份结果选材。这些组装修正已实施，本地验证见新实施报告，不由历史缓存能力推定真实经营效果通过。

例如，第一次取得 GMV、支付订单数，第二次取得 GMV、访客数、转化率：后台保留四项唯一资料；第二次不再重复加入 GMV，也不丢掉支付订单数。下一轮仅选择当前判断及所用证据需要的定义、字段与关联。GMV 公式引用某字段时，指标区保留公式和条件，字段区解释字段；不在每份证据里复制完整公共定义。

继承降低重复检索，但不会让重新发送的内容免计输入 token；每轮占用还要靠选择相关资料和去重控制，费用记录遵循第6.3节。不新增选材、摘要或语义合并模型调用。

### 6.6 执行检查点与重启恢复

用户已确认将服务重启后的原任务继续纳入首版。恢复**已经保存的检查点**，不承诺模型或 SQL 执行到一半还能无缝继续；已完成结果和剩余预算保留，中断调用不自动重放，用户点击继续后按原任务处理。

- **调用前保存。** 在事务中记录动作／尝试、输入版本和预算占用，然后才发起工具或模型调用；并发动作不能重复占用同一份剩余额度。耗时调用不持有长 SQLite 写事务。
- **返回后保存。** 工具结果的数据块、结果索引、动作完成状态和实际用量在同一提交中落盘；引用只有在对应数据已提交后才可用于下一动作。模型更新调查进度、草稿和审核结果时也保存对应修订版本，未经审核的草稿不能恢复成定稿。
- **中断不冒充成功。** 启动时发现仍为执行中的尝试，标记中断／结果未知；不能假定调用没发生，也不能自动重放付费模型请求。已经提交的结果直接复用，未完成部分在用户恢复任务后按剩余预算处理，明确可能的重复成本。
- **恢复前检查范围。** 使用当前登录身份重新校验任务所有者、数据源／快照和结果权限；历史授权不是永久通行证。引用丢失、语义版本变化或快照不可用时，说明具体缺口并只处理受影响内容，不能换一个数据截面补齐。
- **计数随任务恢复。** 普通ReAct轮次、各逻辑SQL生成次数、工具、修复和模型用量不清零。保存累计主动时长和调用计时，不把进程内 `time.monotonic()` 当作跨进程时钟。等待用户和服务停止时间不计主动处理；中断用量以未知／估计保存，与实际值分开。旧token限额不再作为恢复后停止条件，次数和时间限制继续有效。

等待澄清、已完成和已交付状态均从保存记录恢复。第一版不在服务重启后自动发起付费调查；用户在原任务中继续时继承已有证据和预算，不重新跑入口。任务恢复入口需要同时接通后端任务读取和前端继续／追问，不能只完成后端落盘便宣称界面可恢复。

### 6.7 首版范围与边界

首版包含当前任务、同会话追问、授权结果读取以及服务重启后从已保存检查点恢复。跨任务自动学习经营规律、向量化全部调查历史和自动长期业务记忆暂不建设。已有用户主动保存记忆的功能保留，但不把本次调查结论自动写成永久业务规则。

用户已明确：subagent 留待后续版本，首版不做。调查由一个 ReAct 主体维护当前目标、进度和证据；独立最终 Reviewer 继续作为既定交付审核节点，不增加可由调查 Agent 动态派生的子 Agent。第10节同轮独立 SQL 批次仍是工具执行，不因此引入多 Agent 协作。

沿用本方案的稳定任务／动作／结果 ID、来源、依赖和预算记录即可；首版不为未来 subagent 预建派发接口、通信协议、子预算或结果汇总模型。未来确需引入时，再单独设计子任务范围、证据返回、授权与共享预算，并修订方案及验收。

实现顺序：先完成任务与结果统一存储及授权读取，再接进度／语义缓存和上下文选择，最后接检查点、预算恢复和界面继续。历史内存任务只能保存仍能实际取回的内容，旧记录缺失的完整结果或模型用量不能补造。

## 7. 校验、异常、预算和交付

### 7.1 校验边界

校验按下面三类处理，不要求执行前用代码证明所有 SQL 的业务含义。沿用已确认的查询校验简化边界，不为查询批次新增逐步审核模型或通用业务语义证明器。

| 类别 | 检查内容 | 如何处理 |
|---|---|---|
| 执行前必须阻止的错误 | 越权、跨授权快照、失效或越权结果引用、非只读／多语句执行、违反现有外部访问或资源限制；可由元数据或数据库编译明确确认的表字段错误；可明确证明的来源、金额单位、聚合、筛选或时间冲突 | 拒绝相关查询并返回具体错误及依据；安全与授权无法确认时也不执行。影响整个任务授权的问题停止相关任务动作 |
| 执行后及使用结果前的代码检查 | 实际执行状态、返回列、实际输入依赖、结果 ID、完整性及截断；确定性计算；多个结果用于同一比较时的期间、范围、粒度和单位 | 保存每条的实际检查结果；失败、空结果、截断分别处理。不可比或不完整时，只限制依赖这些条件的计算与结论，安排必要补查 |
| 记录为待核对的业务疑点 | 有限解析器无法证明的复杂等价表达、额外筛选的业务影响、尚未对账的指标口径；无法确认的业务名称 | 随证据交给 ReAct 和最终 Reviewer，不据此直接判查询失败、反复重试或一律标为 partial；未核实的指标不能登记成已验证的标准指标 |

具体要求：

- **减少重复声明。** SQL 中的字段、返回列、筛选和聚合优先由程序提取，已识别的注册指标绑定登记定义；不要求模型把同一事实多写几遍，再逐字比对。保留原输出和规范化记录，不擅自改指标含义或 SQL 计算。
- **统一首次生成和重写接口。** 普通查数和调查共用独立SQL模块；SQL首生成和技术修复共用内置database_query规则及后端导出的契约Schema，业务Skill继续由经营ReAct按需选择。模型必须声明metrics的名称、真实来源和聚合；原问题、数据源及可从实际SQL唯一解析的表、分组、简单筛选和时间边界由程序补齐，显式冲突仍拒绝。复杂条件不能唯一解析时明确声明，不猜业务定义或字段。模型Schema只展示物理名称和必要关系；仅可精确映射当前授权图中的内部表ID，任意前缀、越权表和跨快照不能自动去前缀放行。检索继承任务期间和原始时间表达，相关表真实时间列不可因重构丢失。已有规则／契约修复不等同新模块已实施。
- **按实际语义判断明确冲突。** 大小写、中文／技术别名、`<>` 与 `!=` 等已知等价写法不引起重试。CTE、子查询、条件聚合和合法关联不是错误；物理字段检查区分真实表字段、CTE 列及输出别名，不能因简单扫描未找到就硬拦。数据库明确返回编译错误时，按真实技术错误处理。
- **时间不靠搜索字面日期。** 八月范围可以表示为 `日期 >= 2026-08-01 且 日期 < 2026-09-01`，不能因没有 `2026-08-31` 字符串而拒绝。按 DATE／TIMESTAMP、包含／排除终点及已知时区解释范围；能证明漏掉末日或选错期间才判冲突。复杂业务日期表达无法证明时记录待核对，授权快照约束仍必须保证。
- **业务疑点与明确错误分开。** 用数量字段充当已登记 GMV、可确认的金额单位错误、明确遗漏已声明对象筛选，应拦截；仅因显示名称不同、复杂公式未被识别，不得推断错误。安全检查不能降为待核对项，业务待核对项也不能借安全名义升级为拒绝。
- **执行成功与证据可用分开。** 空结果不是 SQL 失败，也不自动代表零；展示预览和截断数据不能当全集。业务疑点未解决时允许继续调查，但不能用它把用户前提认定为不成立并结束调查。最终状态取决于目标是否回答、证据是否充分及实际限制，不取决于有没有一条 pending 记录。

每项硬拦截留下查询 ID、错误类型、SQL／元数据中的具体依据和影响范围；无法指出可核验冲突时，不用笼统的“查询契约不通过”掩盖有限解析能力。基础检查通过也不等于经营原因已验证。不得通过关闭权限或跳过真实查询解决误拦。

### 7.2 预算与无进展停止

| 项目 | 新框架处理 |
|---|---|
| 业务取证 | 最多5轮；每个query查询批次发起即计一轮，失败也计轮；多个独立SQL仍为一批。Skill、检索、日期、读取／计算已有结果、澄清及交付建议不占轮，实际模型决策数另记 |
| 每条逻辑SQL生成 | 总共最多2次：首次生成加一次技术重写。SQL修复不另占业务取证轮，但不能选择业务方向或追加查询；换ID、重组批次和恢复任务不重置 |
| 工具调用 | 保留最多20次初值；真实 Skill 读取、结果读取、语义检索、查询和计算工具调用都计数，失败调用也计数 |
| 非SQL额外修复 | 保留同一逻辑动作额外修复最多2次；SQL遵循上行“总共生成2次”的新规则，不能将它误作额外2次 |
| 主动处理时间 | 保留累计300秒初值，调查最多240秒、预留收尾至总上限；等待用户暂停，恢复继承剩余预算 |
| 前端及底层超时 | 前端保留6分钟初值；底层超时服从剩余主动时间 |
| Token观测 | 只估算、记录实际usage并分开未知用量，不设应用层单次／累计／输出／收尾token硬限制；次数限制不等于人民币金额上限 |
| 旧重规划1次 | 新循环退役该限制；正常选择下一动作不计重规划，也不改名成“只允许换一次方向”。旧字段可仅用于历史兼容，不扩大其他预算 |

Skill 已加载后的复用、后台组织已有上下文、确定性基础校验不算额外工具调用。不得把真实工具动作改为隐式执行来绕过计数。

两次均未成功时，Controller在下一次普通ReAct模型调用之前结束当前调查、进入受控收尾，不能先让模型生成第三份再拒绝执行。当前批次内其余独立查询先分别完成，已取得的有效结果保留用于部分交付。第二次修复成功则可继续后续独立取证。服务重启、用户继续或原记录恢复均继承生成次数，不重新开放失败查询；报告草稿与最终审核继续按原规则处理，不承担SQL重写。该调度修复仅通过本地验证，真实失败不回写通过，见[修复记录](homenova_sql_generation_gate_fix_report.md)。

Controller 比较动作目的、范围、输入证据版本与动作签名：

- 同输入、同错误、相关产物不变时，不继续重复模型修复。
- 已有合格结果满足相同需求时复用，不重复查库。
- 新证据、有效反证、缩小缺口可以构成进展；换 ID、改排版或反复表示“继续思考”不算进展。
- 没有实质进展也没有明确可行的新动作时，转受控收尾；不能无意义消耗完所有额度。

### 7.3 澄清与新目标

纯补参数恢复当前任务、已有证据和剩余预算，不重新运行整个入口。更正时间或口径时使相关结果失效并同步更新事实。

完整新问题或新增目标必须保留整句意图，重新理解其与当前任务的关系；不能仅因出现年份或选项名称就消费成旧任务答案。真正新任务与原任务的参数补充应区分，模型不得自行拆新任务重置预算。

### 7.4 最终交付与状态

正常路径保留“生成草稿→一次独立最终 Reviewer→展示审核定稿”。首版可复用现有草稿生成能力；不额外增加草稿前审核或每步 Reviewer。

最终审核应核对：原问题是否回答、期间与口径、必要证据是否取得、关键替代解释是否处理、缺失能力是否有依据、结论强度是否超过证据。

- 仍有影响核心答案的必要缺口，存在可执行补查／修复且预算允许：返回取证循环，不仅改成 partial 就结束。核心问题已被充分证据回答时可以交付，不因仍能探索更多方向而无限延长调查。
- 证据或草稿实质更新、确有必要时再审；无变化不反复审核同稿。
- 审核通过后直接展示定稿，不再调用模型自由改写。
- 完成、部分完成、等待补充、失败继续对外区分；预算停止且未完成审核须明确标注。
- 不能证明唯一根因不自动等于失败；可以交付有证据、有边界的解释。尚有必要且可行的取证未完成，也不能冒充数据不支持。
- 下降前提被推翻时只停止不适用的归因，保留其他独立问题；没有其他目标时可审核后正常完成，不强制 partial，也不擅自改题调查上涨原因。

## 9. 实施与验收建议

新增独立SQL模块的迁移顺序、组装保真及批次生成验收以[新方案第12节](ecommerce_agent_sql_module_and_context_plan.md)为补充；下列原八类验收继续适用，不缩小范围。本次未获新增真实试跑次数，历史额度与结果保持。

### 9.1 最小迁移顺序

1. 固定 Flash 任务理解、ReAct 动作、结果引用、调查状态与交付请求的最小契约；不先建设通用业务规则语言。
2. 接通单一 ReAct 循环，复用现有检索、MCP、SQL执行与分析基础能力，避免每轮调用整个问答 Workflow。
3. 迁移 Skill 白名单读取与经营诊断方法；同步来源稿和实际注册副本，避免只改 docs 却误认为生效。
4. 按第6节接通 SQLite 任务／结果存储、授权按需读取、进度与语义缓存、证据失效、检查点及预算恢复；接好澄清、有限修复和无进展停止，保护简单查询与已有结果问答。
5. 连接草稿、最终审核和新前端行动记录；逐轮记录模型、工具、Skill、token、耗时和错误。
6. 先跑受控回归和离线数字核算，再在既有授权预算内安排真实业务验收。

### 9.2 固定验收范围

继续覆盖原八类验收：简单查数、正常 GMV 调查、前提不成立、缺参数／数据不支持、错误及修正、预算耗尽、多轮追问、最终交付。预先固定判定标准，不因失败缩小范围。

另增加以下受控场景：

| 场景 | 关键判定 |
|---|---|
| 从整体异常进入 | 先取得必要相关概览，不因模板预设店铺路线 |
| 已指定店铺进入 | 承接对象，复用已有证据；其他店仅在对照有价值时查询 |
| 带看板或原因假设进入 | 区分来源、事实和假设；允许否定假设；明确当前解释对象 |
| 未明确“最近多久” | 有有效期间就继承；没有明确期间及可继承上下文就询问，不擅自默认7天或本月至今 |
| 真实当前时间与快照覆盖 | 所有数据源都按机器真实当前日期解释相对时间；快照未覆盖的期间明确缺失，不当作零、不退回场景日期、不换快照补数据；原有业务时区及DATE／TIMESTAMP边界保持一致 |
| 跨日与恢复期间 | 已解析的绝对期间随任务保存；跨日执行、补其他参数或重启继续时不漂移，用户明确更改期间后才重新解析并处理相关证据 |
| 多轮结果与大表 | 真实结果可复用，按需提供相关数据；计算全集不用预览；引用不越权 |
| 同参数重复失败／无变化交付 | 不靠换动作 ID 重置修复，不重复查库或送审 |
| 同轮多个独立查询 | 同一次模型决策可提出多个查询；逐条计入预算、记录结果和失败，只修复失败部分；需要前一查询结果才能确定参数或方向时，等待真实结果后再决定 |
| 校验等价表达与明确错误 | 常见别名、CTE 输出列和八月半开时间区间可通过；明确越权、跨快照、数量冒充 GMV 及已证明的筛选／时间冲突被阻止，不能靠关闭校验通过 |
| 批次部分失败与预算 | 两条中一条失败时保留成功结果，只修失败项；工具预算剩1次时最多发起1次调用，其余明确未执行；修复计数不因换查询 ID 或重组批次重置 |
| 待核对及结果不全 | 复杂等价表达未被识别不直接触发失败或 partial；空结果、零、预览和截断分别记录，不完整或不可比的证据不用于相关总体结论 |
| 调查记忆与按需语义 | 已取得且仍适用的 Schema／口径从存储复用，不重复检索；模型同时得到当前判断所需数值；不每轮注入全部历史，不新增摘要模型 |
| 语义继承与去重 | 两轮检索部分重合时，同一有效定义在单次输入中只出现一份；新资料补充、旧有效资料保留；不同表同名字段及不同来源同名指标不被误合并 |
| 语义变化与依赖 | 定义版本或授权快照变化时不混用旧口径，冲突有记录；只处理实际受影响的结果与判断，不清空全部资料或触发整项任务重跑 |
| 持久结果与授权恢复 | 重启后仍能按原引用读取超过200行的已保存结果，完整性标志保持；其他用户、任务或快照不能读取；超过保存上限不冒充全集 |
| 检查点与重复执行 | 已完成动作直接复用，中断／结果未知的调用不自动重放；界面从原任务继续，工具、修复、累计主动时间和用量不重置；原有会话归档开关不被误当成完整任务恢复 |
| Token观测与次数停止 | 超过旧token门槛仍可在次数／时间许可下调用，API实际与未知估计分开记录；准备动作不占5轮但仍计实际调用，5个查询批次后不再启动普通调查模型。SQL最多首次加一次重写；恢复不重置且保留历史计数政策。轮次停止时保留证据并受控收尾，未回答目标不冒充完成 |
| 简单答案与调查完成 | 不因执行成功宣布原因成立；有可行缺口返回取证，确实受限才有边界交付 |

模型、流程、错误和超时可用受控测试；业务正确性须由真实模型、真实检索、真实 MCP 和实际数据验证，并在 Agent 外独立核数。Mock 分派成功不等于真实分析成功。

保留历史付费台账和暂停标记，不自动重跑历史题或整套十题评测。2026-10-29用户另行明确授权：本版先做手写SQL探针和本地回归，再最多运行三个不同场景的真实任务；新建独立台账，每题一次，失败计次，不重置旧额度。详见[固定验收范围](homenova_react_v1_acceptance.md)。

## 10. SQL 约束：同轮多查询，每条分别执行

用户已采纳以下三条，并明确校验边界。本轮已接入ReAct独立查询批次及逐条执行、计数和保存；数据库每次仍执行一条只读语句。本地批次控制和真实SQL探针已验证，真实Agent是否采用并完成按运行记录判断。

先区分三个层次：

| 层次 | 决策状态 | 内容 |
|---|---|---|
| 一次用户任务能否执行多条 SQL | 已采纳 | 可以，现有三步调查已经分别执行多条 SQL，不应限制整项任务只能一条 |
| 一轮 ReAct 决策能否提出多个独立查询 | 已采纳 | 允许提出业务取数批次；独立SQL模块可一次生成批内多个SQL，技术修复只处理失败子集，新增模型调用照实计 |
| 一次交给数据库执行的 SQL 文本能否包含多条语句 | 已采纳 | 每次执行一条只读查询；同轮多个查询分别执行，不用分号拼成一段多语句 SQL 文本 |

### 10.1 分别执行的含义

第三条确定多个查询怎样交给数据库执行。以同一轮决定“查店铺指标”和“查商品结构”为例，两种形式分别是：

```text
形式 A：同一轮提出两个查询，系统分别执行
查询1：店铺指标 SQL → 结果 R1
查询2：商品结构 SQL → 结果 R2

形式 B：把两个查询用分号拼成一段文本，交给数据库一次执行
SQL 文本：店铺指标 SQL; 商品结构 SQL;
```

采用形式 A。模型在同一轮提出这两个独立查询，系统分别执行，不要求模型为了提出第二个独立查询而再调用一次。

每个查询对应自己的结果、错误和预算记录，某条失败时只修那一条。形式 B 不纳入本次接口，避免额外处理多结果映射、部分失败及数据库驱动差异。单条 SQL 可以包含合法 CTE、子查询和 UNION；末尾分号及字符串／注释中的分号不应被简单字符串判断误认为多语句。

### 10.2 同轮多查询的执行规则

多指标不等于多条 SQL。同一来源、同一集合和期间内，可以用一条聚合 SQL 同时取得 GMV、相关订单、访客等指标；CTE、多表关联、条件聚合也不因单条语句限制而被禁止。此前只查 GMV、过早按店铺下钻，不是由单条 SQL 限制造成的。

允许同轮多查询时应满足：

- 查询之间没有尚未取得的结果依赖；依赖前一结果来决定对象、参数或方向的查询，等待结果返回后再决定，不预先猜数。
- 每条查询有独立目的、契约、结果 ID、状态及错误；一条失败时保留其他有效结果，只修复失败部分。
- N 条查询仍消耗 N 次查询工具预算，不因包装为一个批次就只计一次；每个逻辑查询继承修复和时间限制。
- 每条都检查只读、权限、数据源／快照和字段；不开放模型写入、建表或经营操作权限。
- 能合并的同口径查询优先合理合并；不同总体或口径不能为追求“一条 SQL”而强行关联。
- 批量提交不承诺一定并发执行或更快；执行策略服从现有引擎能力，查询量和成本如实记录。

例如，店铺核心指标和一个不依赖其结果的商品概览可以同轮提出、分别取证；先识别出异常店铺，再查询这些店铺的明细，属于前后依赖，继续分轮处理。

### 10.3 批次的校验和失败处理

批次只负责组织独立查询，复用第7.1节同一套单条校验器，不再对整批增设一次语义审核。

1. **逐条绑定。** 每条有稳定逻辑查询 ID、目标、SQL、必要口径、真实输入引用和检查状态；返回后绑定各自结果 ID。同批不得引用尚未产生的结果，不允许填造中间数值。
2. **逐条准入。** 执行每条前检查授权、只读、参数、实际依赖及剩余预算。单条确定性格式错误、明确契约冲突或 SQL 错误只阻止该条；独立且合格的查询可以继续。业务待核对项按第7.1节处理。会话授权失效、任务取消或总预算停止时，停止受影响的整个执行流程。
3. **逐条保存。** 成功结果、失败原因、待核对项及完整性分别留痕。失败或未执行的查询没有成功结果可供后续引用；不得为保持批次形状而填零或复制其他结果。
4. **只修受影响内容。** 一条失败不整批重跑；修正查询或上游结果只使实际依赖内容失效。同一逻辑SQL总共最多生成2次（首次加一次重写），技术重写只修原SQL／契约，不另占5轮业务取证。换ID或拆分／重组批次不能清零；生成次数与真正执行SQL次数分开记录。
5. **预算在发起时统一管理。** N 次真实查询工具调用计 N 次，调用失败和重试也计数；包装为一批不合并计费。纯本地预检不另计工具次数，预检拒绝仍记失败及修复；已发起的工具调用即使在工具内部校验失败也计数。每次发起前统一扣取额度，不能让并发查询各自看到相同余量。剩1次就最多启动1次，其他标为未执行；时间上限服从同一任务剩余时间，不给每条各自重新分配5分钟。
6. **使用时检查可比性。** 同批查询可以为不同子问题使用不同期间或粒度；只有需要合并、比较或计算同一结论时，才检查相应范围、期间、单位及集合是否可比。不能因为属于同一批就强求所有查询输出完全相同的字段或时间。
7. **状态跟随目标。** 单条失败或 pending 不自动把整个任务标为 partial。先在预算内处理必要缺口；成功证据照常可用，最终按已回答目标及仍受限内容交付。无可核验进展时按原规则停止，正常路径不增加过程 Reviewer。

动作契约、逐条预算、部分失败处理、界面及本地验收已随本轮实现同步。真实Agent验收限定三个不同场景各一次；不以离线探针或控制分派成功代替真实闭环，不追加第四题来凑通过。
