# 库存事实与条件式风险筛查（inventory_risk_check）

## 适用与边界

回答指定 SKU／仓库在某时点的在库、预占、可售，以及历史缺货、已知采购和条件式覆盖问题。简单查数证据充分即可回答；按真实结果和必要缺口决定是否继续，不预排全部步骤或固定下钻路线。

本 Skill 由当前 ReAct 主体按需读取，只提供业务方法和证据要求。运行层处理语义／结果取得、权限、预算、错误、澄清恢复和最终审核；不派生子 Agent，不执行实时 listing、外部页面、补货下单或调拨。不凭库存事实承诺精确失单、损失金额、唯一经营原因或确定未来安全。

## 必要资料与缺失处理

- 用户完整目标、SKU／仓库范围、观察时点或历史区间、已确认条件与用户已有发现。用户转述的缺货判断先作为线索；只有真实结果可成为已确认事实。
- 唯一绑定数据源／快照的覆盖、观察截点、业务时区、单位和能力；当前机器真实日期／时刻。相关登记指标、字段、粒度、关联及重复风险须实际取得。
- 可用只读查询能力；真实结果 ID、来源 SQL／口径、范围、期间、完整性和检查状态。已有且适用的资料继承，需要新方向时只补缺项。
- 未来风险另需明确评估期限、安全库存／服务水平规则、需求方法与窗口、采购到货和验收可用假设。无登记或用户参数就不自行设默认风险阈值。

“最近”没有长度且无可继承期间时先问；仅真正影响答案的缺失条件需要澄清，不逐次确认补查。缺语义或结果时提出具体需求，不猜表字段。区分未查询、执行失败／结果不完整、口径未确认、能力或覆盖确实不支持。缺未来参数仍可报告库存和采购事实。

## 时间与公共口径

所有数据源的相对时间按机器真实今天和明确业务时区解析，快照场景日期不充当今天。已解析绝对期间在同任务继续和恢复时保持不变。仍只查询绑定授权快照；请求日期超出覆盖时说明，不将缺失当零、不自动退回快照日期、不切其他截面补未来。尾窗末快照不代表持续存在新需求或交易。

以实际提供的公开语义为准，不能凭名称重定义库存：

- 当前公开口径下，在库累计 on_hand_delta，预占累计 reserved_delta，可售为二者差；按 SKU×仓库及 occurred_at、event_seq 重建，保留区间前状态。库存余额不可跨日求和，支付不重复扣库。
- 销售单位不能因 pack_units 自动乘成物理件数。负余额或无法对账要记录并核实，不能强行归零。
- 原计划收货、实际到仓、验收上架分别列示；在途、到仓未验收不算可售。退款资金完成不等于退货验收；仅有实际验收可再售及入库事实才恢复销售库存。
- 支付、发货、退款完成、退货验收分别归期。跨采购、库存、订单和行为事件前先按事实粒度聚合或去重，避免多对多放大。

## 按问题选取证据

| 子问题 | 必要证据与判断边界 |
|---|---|
| 当前余额 | 指定范围／时点、指标单位、完整历史事件或等价可靠汇总；分别给在库、预占和可售。不能仅累计所选短区间的变动当余额 |
| 历史缺货 | 区间起点状态、完整事件顺序和观察终点；重建可售为零的连续区间，按当地业务日切分。当前有货不能否定历史缺货，零销量不能代替缺货证据 |
| 缺货关联影响 | 取得匹配对象与期间的不可售访问、库存阻断等事实；其计数不等于失单或潜在需求，不能换算精确损失 |
| 采购到货 | 按 procurement_id 核对原计划时间／量、当前可知状态、到仓和验收时间／量、对应库存 receipt；purchase_reference 非唯一。未观察到到仓／验收不能假定已入库 |
| 未来覆盖 | 明确期限、需求方法／窗口、可售起点、计划可用时间／量、阈值来源及假设；已记入余额的 receipt 不再次计作未来供应 |

历史销量受缺货和数据覆盖限制，不能直接当未受约束需求。计划到货不写成已发生事实。未触发某个条件规则只可说“在所述条件下未触发”，不能保证安全。

## 取证、充分性与交付

读取真实结果，在原有 ReAct 决策中更新已确认事实、候选解释、反证和缺口，再选择最有帮助的动作。每个关键数值保留结果 ID、字段／指标、范围、期间和计算依据。

查询成功和基础校验通过不证明业务口径正确。预览、Top N、抽样和截断不能作全集；总体筛查使用完整聚合，必要时补剩余汇总或读取授权完整结果。有限解析未证明等价的疑点随结果保留，不能因此自动重试；无法信任的余额也不能被包装为已证实库存事实。

当前库存问题在余额、单位、时点、覆盖、来源和完整性核实后即可完成；历史问题还需起点状态和完整区间。未来风险在方法、参数、期限和约束可追溯时给条件性判断，不扩展未经授权的复杂预测。

存在影响核心答案的必要且可行缺口时建议补查／修复，保留独立有效结果；只有缺用户参数、覆盖／能力不足或预算限制等确实受限时，才说明部分可答内容和未解决部分。单条失败或待核对项不自动把整项任务改成 partial。预算由 Controller 维护，不重置、不无限重复。

正常交付先生成草稿，再独立最终审核一次；无过程 Reviewer，不为每步生成最终回答。实质证据／草稿更新且必要时才再审，通过后展示定稿。

输出按问题需要给范围／快照／截至时点、在库／预占／可售、历史区间、采购计划与实际、条件式情景、真实证据 ID；分别列未查询、查询／口径问题和确实不支持的内容，不把建议写成已执行经营动作。

## 经营与查询分工

经营 ReAct 根据真实证据提出 query_batch 业务取数要求（指标、比较、维度、必要输出及已有结果引用），不生成 SQL 或查询契约。固定 SQL 模块自动复用并补齐相关 Schema、登记口径、样例和关联，逐项取数及受限技术修复；不替经营主体决定下钻方向。Skill 只规定业务方法，不要求经营主体先选择物理字段。资料未取得和数据源确实不支持必须区分。每批计一轮业务取证，技术准备不占轮，实际工具和时间共享预算。

## 问题与证据的持续核对

用户描述保持为待核实线索，不能当成查询事实或推断用户心理。按稳定问题ID维护影响核心答案的待答／受阻项和相关竞争解释，保存支持、反证、范围及证据版本；技术失败不等于问题已回答。报告展示相关指标的正常、异常和抵消变化及未决边界。可选延伸不必穷尽，核心必要缺口有可行路径且预算允许时继续。SQL生成次数以调用方统一账本为准，新任务总共3次（首次＋2次修复）；计算严格按实际工具Schema，不忽略未知参数或将自比较当跨期变化。
