## 两个已定位问题与建议修法

### 1. 同一结果的两种编号混用导致误拦

R1包含：

- 逻辑证据编号：`73765c84d353:R1`。
- 读取引用：`9517699400944f99a5516823f8d482c7`。

S2拿到了完整R1，却把后者填入evidence_ids。现校验只认可前者，将其视为未授权结果。已核对错误引用恰好等于该真实依赖的result_ref，不是未知结果或跨用户引用。

**建议：** 仅在当前步骤已授权依赖集合内，对唯一匹配的result_ref映射到逻辑证据编号，保留规范化记录；比较引用同样处理。未知、非依赖、跨任务／快照或不唯一引用仍拒绝，不关闭权限检查。不增加模型调用。

另需将内层“相同错误／产物无进展”的停止标记传到外层，避免外层重新进入同一步再消耗一次生成；共享额度仍不放宽。

### 2. 阻塞步骤被当成可修复工作，引发重复收尾

第二次审核已修正文案，但Controller仍把S3视为可修复候选。S3依赖已耗尽修复额度的S2，单独重算S3不能恢复执行。此后没有新SQL或新证据，仍生成第三份草稿并审核；后两次审核定稿完全相同，最后又因无变化退出，导致未交付。

第一次文案出现由AOV推断商品结构的无依据表达，退回修正并二审有实际理由；问题在后续无可执行路径时仍循环，而不是所有重复审核都不合理。

**建议：** 判定修复路径时检查上游依赖是否可恢复；不能通过重算下游解决的阻塞不计作可执行工作。已审核通过、有明确边界的事实报告可作为partial交付，未完成下钻要求仍保留；不把Reviewer的complete直接当整项任务完成，也不再用无变化草稿争取放行。

以上仅提出修法，本次没有修改这两处应用代码。先与用户商量，再用本地复现验证，不自动付费重跑。
