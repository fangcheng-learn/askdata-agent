# 电商经营分析 Agent：已确认的设计共识

更新日期：2026-10-28  
用途：记录当前讨论中已确认的产品与架构选择，作为后续讨论和开发的共同依据。  
状态：核心设计共识与Harness V1接入状态。2026-10-28已确认修订：Executor在原有单步调用中读取上游结果、判断本步适用性并输出结构化动作建议，Controller校验及调度；V1暂缓通用规则解释器，不调用独立过程Reviewer，正常路径草稿后最终审核一次，实质变化且必要时才再审。用户随后授权实施，代码已迁移并通过本地回归，两次真实试运行均在查询前失败；“已确认”“已实现”“已验证”“仍待完成”分开记录，最新状态见第6节。

## 1. 产品定位与参考底座

- 面向店铺运营人员，用于日常经营查数、经营变化调查、目标进度分析和库存风险筛查。
- 典型问题包括：“昨天 GMV 多少？”“哪个品类 GMV 下降最多？”“最近 GMV 为什么下降？”“本月距离目标还有多远？”“如何才能达到预期目标？”
- 项目用于 AI 产品经理实习作品集，优先完成有边界、可演示、可验证的经营任务。
- 以 AskData V2 为代码底座，沿用查询与分析双链路、Skill、MCP、澄清和结果复用；适配 V1 Demo 的规划、执行日志和审核回调机制。
- 上下文聚合保留原有模块及流程位置，先补清产品规则；后续发现具体问题时再调整。
- HomeNova 模拟数据和公开语义已经交付，指标口径及数据能力以当前绑定快照的公开语义为准。已有电商数据地图保留为原场景的调查记录，不作为 HomeNova 的数据契约。
- E 阶段报告记录了基础查数通过，复杂经营题尚未达标；数据接入完成不代表完整经营分析能力已验证。

## 2. 整体流程

```text
用户当前问题 + 相关会话信息
    ↓
上下文聚合：理解本轮完整需求
    ↓
入口判断：初始处理路径 + 是否需要多步调查 + 按需选择业务 Skill
    ├─ 简单任务 → 直接查询或处理已有结果 → 验证 → 回答
    ├─ 普通问答 → 直接回答；存在关键歧义时澄清
    └─ 多步经营任务 → Planner 生成初始计划
                         ↓
                     Executor原有单步调用：读取上游结果、前置判断及执行建议
                         ↓
                     Controller（代码）：校验建议、作用范围、状态与预算
                         ├─ 本步适用 → 执行查询／分析、保存结果并代码校验 → 后续依赖步骤
                         ├─ 本步／某分支不适用 → 标记相关要求；继续其他独立目标
                         ├─ 执行或结果有错 → 定向修复
                         ├─ 遗漏关键调查方向 → 回 Planner 调整
                         ├─ 关键业务歧义 → 暂停澄清
                         ├─ 满足交付条件／需有边界收尾 → 生成报告草稿
                         │                            ↓
                         │                     独立Reviewer最终审核一次
                         │                         ├─ 通过 → 展示审核定稿
                         │                         └─ 有问题 → 回Controller修复／补查
                         │                           实质更新证据或草稿后，必要时再次最终审核
                         └─ 无法完成交付审核 → 返回已有结果及明确未完成状态
```

上下文聚合、初始路由和任务模式在职责上区分。实现时可以由同一次预处理模型调用结构化输出，不要求拆成多次模型调用。

## 3. 上下文聚合：已确认的职责

### 聚合内容

- 保留当前用户问题原文。
- 按需读取相关历史对话，理解省略、指代、追问和条件修改。
- 提供相关已有结果的元信息，例如结果 ID、表头、行数、时间范围、指标口径、来源 SQL 和摘要。
- 有活动任务时，读取相关任务状态，包括已完成步骤、已获得的证据和未解决的问题。

### 处理规则

1. 当前明确要求优先；本轮已完整表达的新问题不强行继承旧条件。
2. 有省略时补充必要条件，有指代时明确引用对象。
3. 用户修改条件时更新对应条件，并保留仍然适用的其他条件。
4. 切换任务时重新检查历史条件与结果是否适用，避免污染新任务。
5. 区分已确认条件、实际查询结果和未经验证的推测。

### 聚合后的模型输入

聚合后的完整问题只是后续模型输入的一部分。下游还会按节点职责收到系统指令、Skill、相关材料、已确认条件和可用工具。

- Coder 按需获得相关 Schema、指标定义和查询工具。
- 分析智能体获得相关查询结果、数据来源和分析进度。
- 普通预处理阶段以必要对话和结果元信息为主；详细 Schema 在需要时检索，完整结果数据按需加载。

## 4. 意图路由与任务分流：核心设计已确定

### 保留 V2 的三条初始处理路径

| `route` | 含义 |
|---|---|
| `database_query` | 先获取新的业务数据或项目专属元数据、字段及指标定义 |
| `data_qa` | 先处理已有结果，进行解释、比较、计算或可视化 |
| `direct_response` | 普通知识或能力说明可直接回答；关键需求不明时可先澄清 |

保留路由的依据：查询与分析使用的提示词、上下文和工具不同，入口分流便于管理、调试和优化。

项目专属字段和指标定义须有元数据或已确认规则作为依据；不能使用模型的一般常识代替。

模型输出路由结果后，由 LangGraph 条件分支执行相应路径。条件分支的确定性不代表模型识别一定正确，效果仍需验证。

### 同时判断是否启动 Planner

- 简单查数、处理已有结果：直接执行，并保留结果验证。
- 需要多步经营调查：进入 Planner 和后续控制循环。
- 三条初始路由与是否启动 Planner 不是一一对应关系。
- 路由表示初始处理路径，不将整个任务锁死在一条链路。
- “为什么下降”表示调查目标；是否需要补查取决于已有证据是否足够。不能因为任务同时需要查询与分析，就归入灰色区域让用户自行拆解。
- 进入调查循环后，由 Controller 调度下一步；无需每次工具返回后重新进行用户意图分类。

### 已讨论的典型情况

| 用户请求 | 预期行为 |
|---|---|
| “昨天 GMV 多少？” | 需要新数据时进入查询链路，执行并验证后回答，通常无需 Planner |
| “哪个品类 GMV 下降最多？” | 明确或继承时间、比较基准和指标口径，查询并验证结果，通常无需完整调查计划 |
| “把刚才的结果画成图” | 已有结果满足需求时复用该结果，进入结果处理路径 |
| “最近 GMV 为什么下降？” | 根据已有证据确定起点，进入多步调查；缺少数据时补查 |
| 接着上一轮异常结果问“为什么？” | 继承相关异常、时间和口径，判断证据缺口后继续调查 |
| “本月距离目标还有多远？” | 检查本月目标与实际口径；是否需要多步调查取决于具体请求，不能仅凭“目标”两字决定 |

核心路由方案可以作为后续设计的基线。具体提示词、输出格式和边界案例尚待实现与测试。

## 5. 首版实施方案：V2 底座＋V1 规划与审核

首版采用“Planner声明依赖和适用条件＋Executor同次调用中的前置决策＋代码校验及Controller调度＋独立最终交付审核”。简单任务直接执行；多步经营任务才进入Planner。Executor读取真实上游结果，在原本的单步模型调用中判断本步是否适用并输出结构化建议；适用时在该调用中继续生成本步SQL／查询契约或分析动作，不新增一次判断模型调用。Controller校验建议及实际状态，执行权限、预算、依赖、结果校验与调度。V1暂不建设解释任意Planner业务条件的通用规则引擎，也不调用独立过程Reviewer。正常路径草稿后最终审核一次；发现可处理缺口交回Controller，实质更新后必要时才再次审核。

本节2026-10-28修订取代早前“关键节点／异常触发过程审核”“合并末尾过程审核”及“由Controller解释任意Planner条件”的调度设计；只更新已确认方案，不代表代码已经完成迁移。

### 模块分工

- Planner与最终Reviewer采用独立节点，可以使用同一个模型；V1执行阶段不设置独立大模型过程审核调用。
- Planner生成初始计划，声明目标、依赖、预期产物、前置／不适用条件及作用范围；在Controller判断确需重规划且额度允许时调整。条件供Executor结合真实结果理解，不要求编译成通用规则语言。
- Executor在原有单步模型调用中读取相关上游结果，先判断本步适用性，再输出查询／分析动作、跳过建议或澄清／重规划／交付请求。仅判断本步及Planner声明的条件，不逐步审核全任务质量，不新增判断调用层。
- 步骤代码校验覆盖SQL执行状态、查询契约、输入输出字段、已注册指标口径及时间／单位／聚合约束、结果完整性和步骤依赖。代码检查的适用边界须明确，结构检查通过不等于所有业务解释正确。
- Reviewer只负责最终交付审核：检查草稿、结果与口径、证据缺口及回答完整性；不另设Observation模块，也不逐步调用Reviewer判断是否继续。
- Controller校验Executor建议的动作、证据、条件、影响范围及剩余目标，结合代码校验、任务状态和剩余预算选择执行、跳过、修复、重规划、澄清或交付。权限、预算、依赖等硬约束由代码先行执行；GMV比较等明确计算用代码复核，不依赖模型自行结束任务或重置预算。

### 计划与结果的衔接

采用“步骤编号＋结果编号＋明确依赖”，首版按顺序执行。跨步骤信息保存在共享任务记录中，按当前步骤需要组织输入。

任务开始时，根据完整用户问题形成本次必须回答清单，作为规划与审核的共同依据，不能因为已有结果有限而自行缩小用户目标。

1. **计划声明结果需求与适用条件。** 每步写清子问题与执行动作、输入及依赖、预期产物、代码校验要求、前置／不适用条件及影响的要求和分支；不声明该步完成后调用大模型Reviewer，也不要求Controller理解任意自然语言条件。输入中明确需要使用的字段；引用“前一步的输出”，不提前编造结果；执行后绑定实际结果编号。
2. **执行保存实际结果。** 为每次执行结果分配编号，记录对应步骤、SQL、数据源与快照、时间口径、完整性和检查状态；大结果可保存为可读取的引用。
3. **程序按需传递结果。** 从相关结构化结果提取真实 ID、参数及必要数据，连同口径和结果引用交给下一步，不依靠模型从聊天摘要猜数，也不传入全部历史结果。复用前检查结果是否满足当前步骤的范围、完整性和检查要求。
4. **修正只影响相关步骤。** 上一步失败时，依赖它的步骤等待；重跑产生新结果编号，保留旧结果供追溯。引用旧结果的后续步骤标记为待重算，仍有效的独立结果保留。如果修改全局时间或指标口径，则重新核验所有相关结果。
5. **下一步同次调用中作前置判断。** S2依赖S1时，读取R1的所需结构化数据、来源及口径，结合任务原文、本步目标和Planner条件决定是否建议执行。不适用时返回前提状态、证据、受影响要求／步骤、剩余目标、简短理由及动作建议，不生成该步无意义SQL；适用时直接在同次调用输出执行动作。Controller与完整任务清单核对，不能仅信任模型给出的空剩余清单。

最后一步没有下一位Executor读取其新结果，由代码校验、已有草稿生成及最终Reviewer承接，不额外增加末步过程审核。命中终止／不适用条件后，要求停止扩展该步调查及SQL生成并输出动作字段，不承诺程序可以直接控制或观测模型内部何时“停止思考”。

计划声明需求及条件，Executor读取依赖结果并提出本步动作，代码与Controller校验、约束并调度，最终Reviewer检查实际交付。本次分工及审核调度已迁移并通过受控测试；完整真实闭环仍待验证，历史效果不能代替新方案验证。

### V1审核调用调度

V1不执行中间步骤或异常触发的独立大模型过程审核。Executor只在原有单步调用中作本步前置决策，Controller校验及调度；不增加“先判断一次，再另调模型写SQL”的调用层，也不让Executor逐步重审整个任务。即使判断后不再查询，该次已有模型调用仍有成本。旧实现的`review_after`、`review_reason`不作为新方案模型审核调度依据，迁移留待后续实施。

| 事件 | 代码校验与Controller职责 | 大模型审核调用 |
|---|---|---|
| 步骤执行完成 | 检查执行状态、契约、字段、口径、完整性及依赖，保存结果并供后续依赖步骤读取 | 不调用过程Reviewer |
| 读取上游结果后判断本步是否适用 | Executor在原有单步调用中输出结构化建议；Controller核验证据、条件、影响范围和剩余目标后调度，明确比较由代码复核 | 不新增判断调用或过程Reviewer |
| 空结果、证据矛盾、查询或依赖错误 | 使用现有代码分支定向修复、重规划、澄清或有边界停止 | 不以异常触发过程Reviewer |
| 计划任务完成，代码校验满足交付条件 | 生成报告草稿，组织证据与未完成项 | 独立Reviewer进行一次最终交付审核 |
| 最终Reviewer发现问题 | 判断是否有可执行修复／补查路径及额度，必要时返回执行 | 不因一个未通过结论立即重复送审 |
| 修复／补查后实质更新证据或草稿 | 更新受影响的引用与草稿，记录变化和再审核必要性 | 必要时再次进行最终交付审核，仍共享原任务预算 |
| 同一草稿和证据无实质变化 | 按当前状态受控处理，禁止通过反复送审争取放行 | 不新增Reviewer调用 |

- 只更换ID、版本号、时间戳、排序、空白或排版不算实质变化。送审记录应关联具体要求、范围／口径、实质证据及实际草稿，每次再次审核写明问题、变化和目的。
- 异常优先通过已有代码分支与受控状态处理；Executor无法判断时输出未决问题和所需证据，按适用情况请求补查、澄清或重规划，不用“尚不能判断”证明任务应结束。不临时追加过程Reviewer，未来确需独立复杂业务审核时另行评估。
- 必要的查询生成、步骤分析与Planner重规划仍属于各自职责，不得借其名称恢复逐步Reviewer调用。

### 最终交付审核的完成标准

独立最终Reviewer对照本次必须回答清单、实际草稿与证据，检查三个维度：

- **正确性：** 指标、时间、单位、关联和计算是否符合要求。
- **完整性：** 必须回答的问题有哪些已解决、哪些仍有缺口。
- **证据强度：** 结论属于变化贡献、关联线索，还是有充分依据的原因判断。

| 审核发现的情况 | 处理原则 |
|---|---|
| 必要问题已有可靠证据回答，限制也已说明 | 完成交付 |
| 尚有必要问题未查询，且存在可行调查步骤 | 继续执行；原计划不覆盖时才调整计划 |
| 必要数据或定义经核实确实不支持 | 完成其他可答部分，部分交付并说明缺口 |
| 查询或计算失败 | 定向修复；局部修复耗尽后暂停相关依赖，继续其他仍可执行的必要步骤，再根据有效证据部分交付或报告失败 |

查不到唯一根因，不必然代表任务失败；尚未查询必要数据，也不能当成“数据不支持”。经营诊断可以交付有证据的主要变化来源及有边界的解释，但不能仅凭转化率下降等现象就宣布已经证明根因。

最终审核输出应明确已回答项、证据引用、未回答项、问题类型、受影响步骤和建议动作，供Controller处理；具体机器可读字段仍待细化。发现仍有可执行修复或补查路径时，不能只把任务改为partial并结束。没有实质变化的草稿不得重复审核。

### 特殊情况的处理优先级

| 情况 | 已确认的处理规则 |
|---|---|
| 用户认为下降，实际没有下降 | Executor读取真实结果，返回前提被推翻、证据、不适用范围及剩余目标；Controller复核时间／范围／口径／完整性及比较，只跳过相关下降归因。有独立目标继续执行；没有则生成包含两期数字、变化及纠正说明的草稿，最终审核后可正常completed，不自动partial |
| 比较期缺失、口径不一致或结果不完整 | 前提状态为尚不能判断，修复、补查或必要澄清；不能认定没有下降，也不能借此跳过必要调查 |
| 缺目标值、安全阈值等关键参数 | 先查相关上下文和合法配置；仍缺失且用户可提供时暂停澄清；无法提供时才部分交付 |
| 某一步修复耗尽 | 标记该步失败、暂停依赖它的步骤，继续其他仍可执行的必要步骤，最后统一交付；不自动终止整次任务 |
| 返回空结果 | 先检查筛选、覆盖和语义，不能直接认定为零或数据不存在 |

界面应区分完成、部分完成、等待补充和失败，不能一律显示“查询完成”；实际状态字段仍需接入。

前提被推翻只终止不适用分支，不立即终止整个请求。不自动改题调查增长原因，不切换比较期／范围或挑选局部下降迎合原假设；原任务明确要求的独立目标保留。

### 最终回答与交付审核

正常交付路径采用“必要任务完成或有依据不适用及代码校验 → 生成草稿 → 独立Reviewer一次最终审核草稿及证据 → 展示定稿”。执行阶段采用Executor同次调用中的前置判断、代码校验及Controller调度，不调用独立大模型过程审核。

- 草稿中的关键数字和解释须能对应结果编号。
- 审核发现表述夸大时可以修正文案；发现数据错误时回到执行环节修复。
- Reviewer发现缺口后由Controller判断实际可执行路径及预算；修复／补查产生实质新证据，或针对问题实质修改了草稿后，才可在必要时再次最终审核。新证据同步更新受影响草稿和引用，无变化不重新送审。
- 同一次Reviewer调用给出的已审核定稿可以直接展示，不为同次定稿或排版变化追加审核。
- 审核通过后，展示层只排版，不再调用模型重新发挥。
- 图表使用已审核的结果和范围。

### Controller 的处理与停止边界

Controller校验Executor的结构化建议及其证据、Planner条件、影响范围和剩余目标，依据确定性代码校验、当前任务状态和剩余预算调度；不解释任意业务条件，不建设通用规则引擎。交付阶段再处理独立Reviewer结果，不在每步额外请求审核模型。停止分为正常完成、证据边界导致的部分完成，以及预算或技术问题导致的终止。

- 原计划剩余步骤能够解决问题：继续执行。
- SQL 或执行结果存在错误：定向修复对应步骤。
- 原计划遗漏关键调查方向：回到 Planner 调整。
- 存在影响答案的关键业务歧义：暂停澄清。
- 证据充分，或确实无法继续：交付结论，并说明必要限制。
- 最终审核指出仍有可执行修复或补查路径：回到对应动作，不能仅降级partial并结束；完成实质更新后，必要时再次审核。
- 审核未通过且证据和草稿没有实质变化：不重复送审，按实际未决问题、能力和预算进入受控处理。
- Executor建议跳过或交付：核验前提状态、条件引用、证据和作用范围，与原任务完整要求逐项核对；有独立必要目标时继续，不能因一个stop或request_delivery建议提前结束整项任务。

审核未通过不等于必须重新规划；同一任务内部不重新进行意图路由。

首版采用以下可配置、待实测调整的初值，不代表已经验证的最佳限额：

| 限制项 | 首版初值 | 计数方式 |
|---|---|---|
| 整次任务的工具调用 | 最多 20 次 | 实际工具调用都计数，失败调用也计入；本地代码校验不算工具调用 |
| 单步额外修复 | 最多 2 次 | 格式修正、SQL 修复、执行重试共享额度，不能每一层分别再试两次 |
| 整次任务重规划 | 最多 1 次 | 初始计划不算；改变调查方向或补充调查计划算一次 |
| 整次任务耗时 | 最多 5 分钟 | 计算累计主动处理时间，等待用户补充时暂停；恢复后继续使用剩余额度 |

- 所有内外层重试共享预算，不能各模块分别重试后无限叠加。预算耗尽时返回已确认内容和未解决问题，不宣称完整完成。
- 五分钟内暂按最多四分钟调查、预留一分钟整理与审核分配。前端等待上限暂设为六分钟，给返回结果留余量；底层调用超时也受剩余时间约束。这些均为待实测调整的设计初值，本轮未修改实际运行配置。
- 收尾阶段仍无法完成审核时，返回已有结果和“尚未完成审核”的明确状态，不再生成未经支持的经营结论。
- 重复调查不能只看维度是否查过，需要比较快照、指标、时间、筛选、粒度及所引用的结果。已有成功结果能够满足同一需求时复用；纠错、换条件或检验新假设不算无效重复。
- 没有新增证据、没有缩小缺口，也没有明确可行的新步骤时，停止扩展调查。
- 用户确认仅用于无法从现有信息解决、且会改变答案的关键业务条件。普通补查和下钻不逐次询问；分析建议不等于执行调价、调整投放或补货等经营动作。

### Harness、Skill 与语义层

- Harness 负责流程调度、任务状态、结果传递及执行限制。
- 业务 Skill 提供专项分析方法、证据要求和回答边界，供规划、分析与审核使用。
- 语义层提供指标定义、表字段关系和数据能力边界；Skill 不另行发明指标口径。
- 通用规划与审核能力不依赖新建的三份业务 Skill。专项 Skill 缺失时，可以进行有边界的通用分析，但不能声称已完成缺少方法或参数支撑的专项判断。

### 业务 Skill 的选择与加载

- 沿用入口预处理调用，顺便选择相关业务 Skill，不新增路由或一次模型调用。
- 首次只加载当前任务相关的 Skill 和必要指标语义；普通查数不强制加载完整诊断 Skill。
- Planner可提出补充方法；Executor在本步原有调用中发现方法缺口时可提出结构化需求，Controller核验白名单、任务范围及预算，必要时按重规划结果加载Skill。最终Reviewer也可指出交付缺口。不为选择Skill增加过程审核或重走意图路由。
- 没有匹配 Skill 时使用通用分析规则，并保持已有能力边界。
- 例如 GMV 下降以经营诊断为主，发现缺货线索后再补充库存分析方法。

### 业务 Skill 当前交付状态

- 三份业务 Skill 来源稿位于 `docs/agent_skills/`；Harness V1 已在实际应用目录显式注册副本并注入选中内容。注册与真实效果分开记录，复杂预测仍不在首版范围内。
- 目标值、安全库存阈值和需求预测参数仍需明确来源，不能由模型自行补造。
