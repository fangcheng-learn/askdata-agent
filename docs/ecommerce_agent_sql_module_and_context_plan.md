## 1. 目标与判断依据

目标是让Agent既能可靠取数，也能根据真实结果决定下一步调查方向。需要同时解决两件事：

- **单次查询的资料与执行完整。** 使用真实字段、指标定义、单位、取值、时间和关联；SQL错误有具体反馈与受限修复。
- **多步调查的条件与证据连续。** 后续取数继承已确认范围和口径，复用有效资料、结果和预算，不依靠模型从聊天摘要猜数。

V2已保存的430题报告为SQL执行成功率99.30%、结果正确率82.56%，复杂题正确率33.33%；其评测直接使用预填检索词并调用查询组件，不能当作当前经营调查准确率。拆出SQL模型是职责分工选择，不构成准确率保证。

对照代码已发现需要处理的接入问题：检索字段副本被删除后，部分必要样例／分布信息没有合并到唯一Schema；ReAct二次裁剪可能删除关联中间表；普通查数与调查仍分开组装查询材料。HomeNova现有显式单位、聚合和枚举等改进继续保留，不能为恢复V2行为而回退。

## 2. 整体流程

```text
用户问题＋相关会话／实际取得的看板信息
                    ↓
Flash：路由，整理目标、对象、期间、基准、已有信息、待答问题
  ├─ 普通交流 → 原有直接回答
  ├─ 已有结果问答 → DataQaAgent → 回答／按需报告
  ├─ 简单查数 ────────────────────────┐
  └─ 经营调查                         │
         ↓                            │
    经营ReAct                         │
    读取业务Skill、目标、进度、真实证据 │
    提出本轮取数要求，不写SQL          │
         ↓                            │
    Controller绑定批次／查询ID与预算   │
         └──────────────┬─────────────┘
                        ↓
                 统一SQL查询模块
           代码组装本轮完整查询资料包
           复用已有语义，只检索必要缺口
                        ↓
           SQL模型：生成本批独立SQL
                        ↓
           代码校验／编译 → 真实MCP执行
             ├─ 可修技术错误 → 只重写失败项
             └─ 保存每条真实结果／状态／引用
                        ↓
           调查：返回同一经营ReAct看结果
           简单查数：进入原结果整理与回答

调查满足交付条件／需要有边界收尾
               ↓
       直接调用同一DataQaAgent生成报告草稿
               ↓
       独立最终审核 → 展示定稿
```

SQL模块是应用内固定受控组件，使用独立的SQL生成调用，可以沿用现有模型配置；不建立动态subagent、子会话或任务派发平台。调用一次SQL模块，不等于调用一次完整问答Workflow。

## 3. 职责与边界

| 部分 | 负责 | 输出／边界 |
|---|---|---|
| Flash | 理解用户本轮问题并选择初始路由 | 不选择Skill、不规划调查、不生成SQL；调查内不重复路由 |
| 经营ReAct | 选业务Skill、看证据、提出和检验解释、决定取证方向或交付 | 输出业务取数要求、进度更新和简短目的；不承担物理字段检索、SQL编写和技术重写 |
| 提示词组装器 | 从同一后端记录选择、补齐、去重和组装输入 | 代码实现；不新增选材、摘要或记忆合并模型 |
| SQL模块 | 准备相关查询资料、调用SQL模型、检查与执行、受限修复、返回结果 | 不改变经营目标，不自行扩大范围或追加调查任务，不逐条写最终用户回答 |
| DataQaAgent | 在原有data_qa入口分析已有结果；在调查收尾整理多份证据并生成报告草稿 | 复用同一模块，用不同任务模式和输入组装；不新增自主分析循环或独立长期记忆，不重复路由 |
| Controller | 管理身份、范围、状态、依赖、次数、时间、并发和停止 | 对执行与持久化负责，不尝试用规则解释任意经营原因 |
| 最终Reviewer | 审核草稿、目标覆盖、证据及结论强度 | 正常路径一次最终审核；没有过程Reviewer |

业务Skill由ReAct按需从白名单选择并实际加载，负责方法和证据要求。复杂调查优先读取适用方法，也允许先核实数据后补读；业务Skill不是SQL执行前提。只有读取正文后才能声称依据该方法行动。`database_query`作为SQL模块的内置技术规则自动提供，无须ReAct选择。SQL模块不自动加载三份业务Skill，也不扫描docs或仓库。

经营ReAct仍需理解相关指标的业务定义、单位、可用维度和能力边界。通常无需完整物理字段图、SQL语法规则和历史候选SQL。轻量能力说明从授权公开元数据取得，不另造独立能力注册平台，不假定所有数据源都有流量、转化或价格证据。

## 4. ReAct怎样提出取数要求

一次业务取证批次包含一个或多个相互独立的查询目标。每项至少说明：要回答的问题、指标要求、比较方式、必要维度或输出、真实输入结果引用，以及与用户目标的关系。

示意，非固定任务模板：

```json
{
  "action": "query_batch",
  "purpose": "核实GMV变化，并区分订单数量和每单金额的变化",
  "queries": [
    {
      "goal": "取得当前范围内两期GMV、支付订单数、商品销量和订单客单价",
      "metric_requirements": ["GMV", "支付订单数", "商品销量", "订单客单价"],
      "dimensions": ["比较期间"],
      "input_result_ids": []
    }
  ]
}
```

- 不要求ReAct填写物理表字段或重写用户已确认的全部时间条件。程序绑定任务约束，输出组装后的最终范围供追溯。
- 原问题保留整项经营目标，单次取数目标明确本条SQL的职责。校验针对本次目标及实际适用的继承条件，不能要求每条SQL回答整个用户问题；维表／元数据查询没有事件时间含义时不强塞交易时间筛选，也不能借此省略事实查询应有的期间。
- 指标优先引用已取得的登记ID；只有业务名称时由公开元数据解析。多个同名来源会实质改变答案且无法消除时请求澄清，不猜来源。
- 省略条件表示继承；显式空值不能清除已有约束。改变范围必须有用户指令或服务于原目标的明确对照目的，不能由SQL模块悄悄扩大。
- 额外对象或比较条件使用可选 `conditions` 业务对象结构化表达，省略表示继承，不用空值清除已有任务约束；不能只把不同筛选藏在目标文字中。目的说明不参与重试额度身份。
- 后端分配稳定 `batch_id`、`query_id`，绑定任务、用户、快照、需求版本和输入证据；模型不能自行换ID清零。
- 同一口径、集合与期间的相关指标优先合理合并。需要上一结果才能确定对象、参数或方向时，下一轮再提出，不能在同批引用未来结果。
- 预检发现缺参数、能力或资料时返回具体缺口，不将“未检索到”直接写成“数据源不支持”。

## 5. 一份后端记录，按角色组装输入

### 5.1 保存到哪里

继续复用现有 `backend/data/harness_runtime/state.sqlite3` 和任务内语义池、调查进度、结果引用及预算。内存只作缓存；不新增SQL Agent独立聊天历史，不建立另一份Markdown权威记忆。

| 共享记录 | 保存内容 | 主要更新者 |
|---|---|---|
| 任务约束 | 原问题、目标、对象、绝对期间、基准、时区、授权快照、用户已有发现与来源、待答问题 | 入口整理，Controller提交；澄清后定向更新 |
| 语义资料 | 表字段、关联、指标定义、单位、状态／必要样例、覆盖、空值含义、来源和版本、已加载Skill | 授权检索与代码合并 |
| 调查进度 | 已确认事实、候选解释、反证、已否定解释、未解决问题；事实绑定证据版本和适用范围 | 原有ReAct调用提出更新，服务端提交 |
| 证据与执行账本 | SQL、候选、错误、真实结果、完整性、依赖、检查状态、生成／执行次数、实际调用用量 | SQL模块与Controller |

模型提出的原因不会因写进进度就自动成为证实事实。进度更新使用显式新增、修订、失效或关闭，不因本轮没提及而无声删除旧有效事实。

### 5.2 经营ReAct输入

每轮重新组装：

1. 稳定任务目标、范围、期间、基准、用户已知信息及来源。
2. 已加载业务Skill；尚未加载时提供白名单名称及适用说明。
3. 当前业务指标定义、单位、公开能力边界和可用分析维度。
4. 调查进度：事实、假设、反证、未回答问题。
5. 本轮相关证据的真实数值／适用聚合、期间、范围、检查与完整性，以及其余证据的可读目录。
6. 上一步结果或结构化错误、剩余轮数／工具／主动时间。

证据选择同时考虑本轮需求、活跃事实／假设、未解决问题及真实依赖，不只选择最后两份结果。目录ID不等于已提供数据：需要早期R1的数值时，按权限读取所需列或完整聚合后再组装。

### 5.3 SQL首次生成输入

| 区块 | 必须包含 |
|---|---|
| 固定技术规则 | 查询专用职责、DuckDB方言、只读与输出格式、真实字段使用规则、关联与聚合原则、总生成上限 |
| 当前查询批次 | 后端绑定的查询ID、每项具体取数目标、指标／维度／输出要求、与原任务的关系 |
| 继承条件 | 原问题及已确定对象、绝对时间、基准、业务时区、授权数据源／快照、用户确认参数 |
| 相关指标口径 | 正式定义、公式、单位、事件时间、必要筛选、分量政策、依赖及成熟度；不只给指标名 |
| 物理Schema | 真实表／字段名称、类型、粒度、必要键、完整关联路径；不把内部索引ID当SQL名称 |
| 取值与覆盖 | 必要合法枚举／代表样例、来源与适用范围、币种、日期覆盖、观察截点、空值含义 |
| 实际依赖 | 本次确实需要的结果ID／版本及真实列值或聚合，不能只传聊天摘要或模型抄写数值 |
| 统一输出Schema | 从后端实际协议导出；每项只返回绑定query_id、SQL、必要指标声明及简短技术说明 |

同一批次内共用的定义只出现一次，各查询保留自己的条件；不为去重抹掉不同时间、粒度或统计集合。原始完整日志、全部调查假设、最终报告和私有评测资料不进入SQL输入。

### 5.4 技术修复输入

沿用同一查询目标、范围和相关资料版本，并加入：原候选SQL／契约、具体错误阶段与原始诊断、可用字段或类型等针对性信息、已用生成次数。首次与修复共用同一技术规则及输出Schema，不能退化为“根据报错重写”的简略提示。

修复可补充真实缺失字段或关联，必须记录补取来源及变化；不能偷偷换指标、时间、用户对象或业务方向。SQL模块若发现真正的业务歧义，返回结构化缺口，由Controller进入原任务澄清或交ReAct判断。

## 6. 资料复用、去重与补查规则

组装顺序固定为：**确定需求 → 复用适用资料 → 补查缺口 → 补齐必要依赖 → 去重 → 输出本轮输入。**

- 字段／指标以数据源、授权快照、稳定ID和版本识别。不同表同名字段、不同来源同名指标不能合并。
- 相同有效版本复用；互补属性合并；定义、单位、状态或版本冲突留痕并核对权威来源，不让模型自动揉成一个定义。
- 新检索没有命中旧字段时仍保留旧有效资料。Schema或口径适用时继承，只有新缺口才检索；不能每轮重查一遍。
- 按指标定义补齐分子分母、状态、事件时间及相关字段。涉及两端表关联时，补齐完整中间路径、桥接表和连接键，然后再裁剪无关资料。
- 保留唯一有效的取值、单位、覆盖、空值和计算定义，不能删除整个检索区块后假定Schema已包含。大段profile可提取必要结构属性，不把事实依据压成模型自由摘要。
- 样例是合法取值或形态的证据，样例日期不是完整覆盖，枚举也不自动等于出现频次。标明来源和适用快照，不用未来截面的画像补旧快照。
- 每轮从后端重新组装，不把上一轮提示词、历次检索结果和整份聊天历史逐轮追加。每个有效定义在单次输入中只有一份；跨请求重新发送仍计输入token。
- 原始结果继续保存于后端，按引用读取。预览200行、保存上限50,000行、授权分页最多1,000行分别标识；总体计算使用完整聚合或完整可用结果，不能拿预览替全集。
- 用户修改期间／对象或语义版本变化时，保留历史记录，只使实际受影响证据和判断失效；独立有效结果保留。

所有相对时间仍使用机器真实当前时刻；无可继承期间的“最近”先问长度。同一任务已解析的绝对期间不逐轮滚动；超快照覆盖不当零、不自动改期或换快照。

## 7. SQL模块的执行与修复

### 7.1 批量首生成，逐条执行

首版默认一个业务批次调用一次SQL模型，生成批内多个独立查询；资料包按批次去重。模型只能返回后端分配的查询项，不能自行追加查询ID或业务目标。

每条分别校验、编译、真实MCP执行及持久保存；当前批次串行执行，服从同一剩余时间和工具预算。需要不同统计集合的指标不能为省调用强行关联。简单查数复用相同模块，作为单项批次，不引入经营ReAct。

按批生成是复用V2查询思想后的接口适配，不是声称原V2已有该能力。不得在外面包装批次、里面仍无记录地逐条额外调用模型。

### 7.2 每条逻辑SQL总共最多生成三次（新任务已接通）

| 情形 | 计数与处理 |
|---|---|
| 一次模型调用首生成Q1、Q2 | Q1和Q2各预占第1次；Chat实际只有1次，token只记一次 |
| Q1成功、Q2失败 | 保留Q1；下一次调用只修复Q2，预占其下一次生成额度，最多首次＋2次修复 |
| 多项失败 | 可以一次技术修复调用处理失败子集；每项分别占其剩余次数，不包含成功项 |
| 整批JSON无效／输出缺项 | 对已请求的查询保留这次生成尝试；有效可归属项保留，仅修失败／缺失项 |
| 网络中断、超时或结果未知 | 调用前记录占用，不能因没有执行SQL就返还；重启不自动重放 |
| 第二次仍失败 | 若错误可修、剩余额度／时间／工具允许，可发起第3次生成，只处理失败项 |
| 第三次仍失败 | 禁止第4次生成；关闭该逻辑查询，保留其他成功结果。Controller按第14节判断其他可行取证或有边界交付，不自动停止整项调查 |

这里约束的是针对绑定查询的SQL生成请求，实际产出候选数量、真实数据库执行次数、未返回结果的未知尝试另行记录。Schema缓存读取和确定性准备不是生成请求。SQL节点返回真实缺口／请求澄清时，保留已经发起的调用及占用，恢复不清零。

不能继承V2的“内层三次格式修正＋外层多次执行重试”。模块、调用方、模型SDK及HTTP层共享同一本账；SQL生成／重写禁用隐式网络重试。若更改模型节点名称，必须同步现有重试保护，避免只保护旧 `query_coder/sql_repair` 名称。

逻辑查询身份绑定规范化业务需求、对象、期间、指标、粒度、输入结果版本及来源，不只比较一句目标措辞。换query_id、重排批次、修改说明不能重置。用户真实修改需求可以创建新的需求版本，但任务轮次、工具与主动时间不清零。

### 7.3 检查与结果返回

沿用已确认的校验边界：

- 代码强制权限、授权快照、只读／单语句、外部访问限制、真实表字段、有效结果引用，以及能证明的来源／单位／聚合／筛选／时间冲突。
- SQL里的机械字段由程序尽可能提取；模型只声明必要指标含义、来源和计算。显式冲突不能用补全覆盖，不靠日期字符串是否出现决定区间正确。
- 合法别名、CTE、子查询和复杂等价表达不能只因有限解析未识别就拒绝。未证明的业务疑点随证据保留，SQL成功不认证经营口径或因果结论。
- 编译／执行错误向修复节点提供具体原因；存储失败、权限拒绝、数据能力不足或模型服务故障分开处理，不一律让SQL模型重写。
- 每项结果返回ID、实际SQL／契约、列与数据、单位和范围、完整性、引用、检查状态、依赖及错误类别。SQL模块不直接将整个调查改成completed或partial。

查不到记录不自动等于零，取不到指标不自动否定用户前提；只有实际证据能说明前提不成立。下降被推翻时停止不适用的归因，处理其余独立目标，无其他目标时按证据进入最终审核，不自动改题调查上涨。

## 8. 预算与交付继续共用

| 项目 | 本方案规则 |
|---|---|
| 业务取证 | 最多5轮，一个query批次计一轮，失败／准备后未成功也计；简单查数不增加经营ReAct循环 |
| SQL生成 | 新规则每条逻辑查询总共最多3次（首次＋2次修复）；批内各自计数，技术重写不再占取证轮；新任务3次，旧任务继承原账本上限 |
| 工具 | 总共20次；SQL模块包装不重复扣一次，但内部真实检索、Skill读取、结果读取、查询和计算均照实计，失败也计 |
| 时间 | 主动300秒，调查240秒，剩余收尾；等待用户暂停，恢复继承。SQL模型、检索和底层工具超时服从剩余时间，前端360秒 |
| Token | 估算与记录API实际usage，不设应用层token硬限制；未知用量与估算分开 |
| 审核 | 正常路径草稿后一次最终审核；无过程审核，也不增加独立记忆／摘要模型 |

SQL模块自动准备技术资料，ReAct不必为每个物理字段发起决策；业务Skill选择与方法阅读仍保留真实调用。纯缓存读取和代码组装不冒充一次新检索，也不隐藏真实Embedding／Rerank费用。

第5批结束后沿用既定受控收尾，不再开放第6批调查。Reviewer发现必要缺口时，若存在可执行路径且预算允许交Controller处理；确实受限时交代已有结论和缺口。证据或草稿没有实质变化不能反复审核；审核通过后直接显示定稿。

外部状态沿用completed、partial、waiting_clarification、failed等现有状态及审核标志。预算停止但未完成最终审核须明确展示，不能将SQL模块成功当作调查完成。

### 8.1 复用DataQaAgent，保留两个调用位置

用户已确认：V2图中的Data-Analysis Agent对应源码的DataQaAgent；`data_qa`是进入该能力的路由名，也是对应Skill名。它们不是两个独立分析智能体。

| 调用位置 | 输入与输出 |
|---|---|
| 原data_qa路由 | 分析上下文中已有的结果；保持原有普通回答／用户要求报告时生成报告的选择 |
| 经营调查收尾 | 由Controller直接调用同一个DataQaAgent，传入完整调查目标、范围、进度、有效证据和缺口，默认生成调查报告草稿，不要求用户额外说“写报告” |

使用后端明确的调用模式区分二者，不靠模型从问题是否含“报告”判断调查收尾输出。复用共同报告能力和数据引用检查，原有普通问答行为不被调查模式覆盖。

调查收尾不重走Flash或整个问答Workflow，不更换任务ID、会话、授权快照和预算。DataQaAgent共用后端记录，不维护另一份长期聊天，也不首次重新开展整项原因调查；经营判断和取证方向仍在ReAct循环中形成。

DataQaAgent替代本方案原有的报告草稿生成调用，不在草稿前再叠加一个整理／分析模型。若发现证据缺口，随草稿明确提出，交现有Reviewer与Controller判断是否返回原取证循环；DataQaAgent不自行调用SQL模块补查。

### 8.2 报告的内容、图表与最终展示

报告按用户阅读顺序组织，内容长度随任务复杂度调整：直接回答原问题；列核心指标对比和单位；解释主要发现及支持／反证；必要图表；限制与后续建议。可展开的证据、SQL和执行记录保留，过程日志不替代业务结论。

复用V2的Markdown报告组织、已有图表能力和报告卡片／导出机制。图表按需要使用，不要求固定数量；不能把贡献图当成根因证明。趋势按时间顺序、排名按实际指标排序；有负值的下降贡献不能用截掉负数后重新归一化的饼图表达。

多步调查的报告数据源须绑定具体结果ID与版本，不能只靠整个task_id识别某张表。正文、对比表和图表使用同一份真实证据；图表数据由后端按合法引用取得，不让模型重新填写数值。币种、单位、精度和完整性来自结果元信息，不能仅凭中文列名推断人民币或把预览当全集。

同一次草稿调用形成正文及必要图表规格，代码检查引用和字段；最终Reviewer同时审核正文、表格、图表规格与实际数据。审核修正文案时同步核对相关图表，只有获批的完整报告产物才展示。通过后仅做确定性渲染与格式化，不再调用模型润色、补图或改结论。

实际使用MCP展示工具时计入原工具预算，前端纯渲染不增加模型调用。图表不是交付的强制条件，不能为了图表绕过预算或再次查询已经取得的数据。部分完成的报告明确已回答内容、缺口及停止原因；未完成审核时按原状态标注。

## 9. 调用成本怎样看

独立SQL生成会增加一类模型调用，同时可减少经营ReAct反复携带物理Schema、SQL规则和技术报错。两者的总token与耗时必须实测，不能先承诺更省钱。

示例仅用于解释计数：3轮取证，每轮一个查询批次，无修复，业务Skill已加载，另有一次请求交付决策，则Chat为：入口1＋经营ReAct取证3＋SQL首生成3＋交付建议1＋草稿1＋审核1＝10次。若额外发生一次选择／读取业务Skill的ReAct决策，再增加1次；Embedding／Rerank另记。实际可以提前交付或出现修复，不能拿示例当固定流程。

其中“草稿1”即调查收尾的DataQaAgent调用，不再另外增加一次Data-Analysis或data_qa整理调用。

批次有多个独立SQL时，首生成仍可为1次Chat，真实MCP调用分别计。每次Chat记录关联query_id列表，usage只计一次；没有接口级依据时，不把整次token重复摊算成每条SQL的实际账单。

## 10. GMV调查示例

用户：“2026年7月GMV为什么比6月少？感觉销量还可以。”以下是条件分支示意，不代表真实数据结论。

1. Flash明确原因调查、当前授权范围和6／7月比较，保留“销量似乎还可以”作为用户线索。
2. ReAct加载适用业务Skill，提出当前范围的GMV、支付订单、商品销量及订单客单价比较要求，不预设店铺下钻方向。
3. SQL模块复用公开语义并补齐真实字段、支付状态、事件时间、单位和关联，生成并执行查询，保存R1。
4. 假如R1显示订单稳定而客单价下降，ReAct决定进一步检验商品结构或成交价格解释；销量与订单数分开，不能偷换。
5. SQL模块继承同一对象、期间和口径，只补商品等新资料。若本轮需要总体贡献，用R1引用读取真实总体；不让ReAct重新抄一个数值。结果保存为R2。
6. ReAct结合R1／R2判断解释是否充分；必要可行时继续，不将商品贡献直接当成根因。能力或预算限制真实存在时说明边界，进入草稿与最终审核。

用户已指定某店时沿该店开始；用户问看板中流量下降原因时沿流量目标开始。核心指标概览针对当前分析范围，不固定从全平台GMV重查。

| 第二份SQL几乎照抄 | 错误传递存在，但诊断偏机械，修复未对照具体冲突和实质变化 | 错误协议、受限修复 |
| 跨期计算变成自己减自己 | 工具参数及数据形状没有严格约定，未知参数被忽略 | 通用计算工具协议 |
| 用户线索变成事实／心理解释 | 原文、用户发现、假设与真实证据没有贯穿整个任务保持区别 | Flash输入、调查记录、报告 |
| 未完成原因调查却completed | 当前核心缺口和完成证据没有逐项对账；审核可自行缩小目标 | 调查问题记录、Controller、最终审核 |
| 输入越来越大 | 有缓存继承，但调用组装器时没有选择本轮指标／字段 | 角色输入组装 |
| 报告只有支持某个结论的数字 | Skill缺少可操作的比较关系、竞争解释和证据覆盖要求 | 经营诊断Skill、报告组织 |

这是一组通用接口及业务方法修订，不针对某条SQL写例外，也不建设能够证明任意SQL业务正确的规则引擎。

### 14.2 查询前先形成明确的度量说明

经营ReAct继续用业务语言说明本轮要回答什么。查询模块负责把它解析成一个小而明确的请求，复用现有公开指标与Schema，不新增能力注册平台或额外选材模型。

每项度量至少明确：

- 原始问题／待答问题ID、本轮取数目标及实际结果依赖。
- 已登记指标ID，或当前任务内定义明确的临时度量；两者标识不同，临时定义不自动写入全局指标库。
- 统计对象和粒度：订单、商品件、会话、用户、事件、金额或比率等；适用计数键和去重／聚合政策来自实际公开定义。
- 统计集合、对象条件、事件时间、期间／基准、业务时区及观察成熟度。
- 单位、币种、税费和退款处理；比率的分子、分母及共同集合。
- 返回列与业务指标的对应，以及供下游读取的范围、完整性和证据版本。

已登记信息由程序绑定。实现时在现有语义对象上按需补充统计对象、计数／聚合键、事件时间及统计集合等少量结构字段，不新建注册平台；来源只能是公开登记资料。源定义确实不足时保留缺口，不能从私有题目或参考SQL反推口径。名字未匹配成功时，先查公开别名／依赖；不能检索一次后就把未解析要求标为已具备。对于“加购会话数”等尚未登记但公开字段足以构造的量，可以在原SQL生成调用中给出清楚的临时定义和来源，再校验和记录；不增加一个专门解释指标的模型。真正会改变用户答案的歧义才澄清，技术资料缺口由模块补查。

按集合、事件时间和粒度组织查询：同一集合指标合理合并；不同统计集合可分别聚合或形成同一业务批次的多个独立SQL，不能用同一个WHERE强行统一。后端在首次生成前绑定执行子项ID，一批仍可一次Chat生成，分别执行和保存；成功项保留。

例如支付结果按支付事件归期，会话漏斗按会话开始归期。二者可以并排比较，但不能因为同是“7月”就直接拼成同一个恒等式。事后拆分或改名不得重置原需求已用生成次数，新增子项继承原项已消耗额度。

### 14.3 技术修复：最多三次，有明确诊断

每条逻辑查询总共3次：第1次首生成，第2、3次仅修复可修错误。生成请求在调用前预占并持久化；格式无效、缺项或未知响应保留已用次数；批内按项计数，Chat实际只记一次。禁用内层／SDK／HTTP隐式重试。

首次和修复共用同一技术规则、实际输出Schema和适用资料版本。反馈除原始错误外，提供能从代码与公开定义确认的内容：

| 内容 | 示例含义 |
|---|---|
| 阶段及类别 | 参数、格式、真实字段、类型、SQL编译、执行、明确口径冲突、权限、资料或服务故障 |
| 出错对象 | 绑定query_id、指标／输出列、相关SQL表达式或参数路径 |
| 当前实际含义 | 实际统计对象、实际引用字段或已识别事件时间 |
| 期望及依据 | 当前查询要求和公开登记定义，相关合法字段／类型／枚举 |
| 受影响范围 | 失败项及实际依赖，哪些成功项必须保留 |
| 剩余额度 | 已用生成次数、剩余时间／工具、不能更改的用户条件 |

不能确认的语义不伪装成代码已证明。修复后的规范SQL／结构化请求与旧候选相同、同一冲突仍存在时，记录无实质修复，不重复执行相同失败产物；如仍有一次额度且存在可执行修法，可在原账本内继续，绝无第4次请求。

权限拒绝、缺失用户参数、结果存储故障和供应商服务故障分别处理，不机械花完三次SQL修复；未知远程结果不自动重放。第三次上限是允许的最大值，不要求每次用满。增加次数不延长当前300／240秒预算。

校验继续强制权限、只读、快照和能证明的字段／来源／单位／聚合／时间冲突。复杂等价表达保留待核对项，不新增日期字面量、命名习惯或自然语言关键词硬拦。应减少含糊需求和重复手抄，而非层层增加通用拦截规则。

### 14.4 计算工具使用明确的数据与参数协议

问题不只在某次GMV计算，而是工具把“列存在”当成了“操作有意义”。修订全部受控计算操作的参数格式，从同一后端Schema生成工具说明和校验；不支持的字段不能静默忽略。

- 原逐行变化／比率：明确同一行的两列，适用对象和分母；无意义自比较不能冒充跨期变化。
- 跨期比较：显式指定期间列、基期、本期、数值列、可选分组键；直接读取已有完整长表，不为简单透视重复查数。
- 求和／列统计：明确是否可加；期间去重用户数等不能按日简单相加。
- 分组贡献／两因素分解：使用固定且说明清楚的方法、同一统计集合、完整总量和可核对的抵消项；不执行任意模型代码。
- 缺期、重复期间、空值、零分母、非数值、结果截断和分组键不唯一分别返回明确诊断，不自动补0或默认合并重复行。

产物带操作、参数、输入结果ID／版本、范围和检查状态。错误参数不能产生basic_valid计算证据。上述规则适用于销量、库存、退款和广告等任务，不按GMV列名编写专门分支。

### 14.5 调查记录：原问题、线索与核心缺口逐项保留

入口只明确原目标、对象、期间、基准和用户已有信息；用户说“销量还可以”保持为未核实描述，不改写成“销量未下降”或“用户存在认知偏差”，也不提前安排退款、折扣等具体原因。

已有调查记录增加稳定的问题／解释ID与少量状态，不重新建立Planner：

| 记录 | 作用 |
|---|---|
| 原始目标 | 用户实际要求，不能因查询失败被缩小 |
| 用户线索 | 原文、来源、范围、是否已经用适用证据核实 |
| 当前核心问题 | 与原目标的关系、影响答案的程度、待答／已答／受阻／有依据不适用 |
| 候选解释 | 考虑依据、支持／反证、尚缺什么、证据强度、下一项有区分力的取证 |
| 查询结果 | 对应问题、实际值、口径、完整性、版本、技术失败及剩余额度 |

这些状态在原有ReAct调用中更新。未提及不删除旧事实，写入假设不自动成为事实。核心缺口与可选延伸分开：新问题若可能推翻主要结论，应继续处理；只是额外探索不能无限延长任务。

### 14.6 单条查询失败与整项任务停止分开

SQL三次失败后关闭该逻辑查询，返回具体阻碍及已尝试内容；成功证据保留。Controller不因此把整个任务直接送交付。

若仍有调查时间、工具及5轮取证额度，主Agent在原有ReAct调用中判断：

1. 能否通过确实不同的证据回答同一核心问题，或继续独立且必要的问题。
2. 是否存在仅需用户补充的参数；有则等待并保留任务与预算。
3. 无可行路径时，交付已经核实的内容及仍缺什么。

同一失败要求换名称、换ID、重排批次或拆SQL不能获得新额度；不允许用所谓新方向继续同一份失败SQL。技术失败、能力不足、没有记录和已被反证分别处理。

任务停止仍由总预算、权限、无进展、无可行路径或目标已回答决定；5轮、20工具、调查240秒／主动300秒不暗中放宽。依赖失败只阻塞受影响内容。新任务已使用该分支；旧任务继续保留原协议和上限，不重新执行或返还次数。

### 14.7 经营诊断Skill：对比清单、关系和取证分支

采纳用户提供的四层方法，写入经营诊断Skill作为业务章法。它约束应回答的问题和证据，不强制每次按四个固定步骤执行，不预设店铺／渠道／SKU是原因。

| 对比层次 | 相关指标／证据 | 要回答的问题 |
|---|---|---|
| 经营结果 | GMV、支付订单数、支付商品件数、订单客单价 | 变化是否真实，减少主要体现在哪些量上 |
| 订单与商品构成 | 每单件数、平均每件实付金额、SKU组合、适用折扣和同SKU成交价 | 每单金额变化来自数量、同类价格还是商品组合 |
| 获客与成交 | 有效会话、购买会话、购买转化率、每个购买会话订单数、可用渠道／商品维度 | 变化出现在哪些来源、对象或结构中 |
| 具体成交障碍 | 加购、结账尝试、成功支付、库存阻断及适用的价格／履约等事件 | 哪一环节或经营变化与异常相符，有什么支持与反证 |

GMV任务优先取得／复用当前范围同口径的G（GMV）、O（支付订单数）、Q（支付商品件数），派生A（G/O）、U（Q/O）、P（G/Q）。需要且有定义的流量／转化指标可作为同一批的独立查询取得；不能为省调用混集合。不适用或资料缺失项明确标注，先确认能力，不把未加载当不支持。

用户指定对象就在该对象内建立概览；用户已有看板证据先验证／复用其范围和口径；用户问流量原因则沿流量调查，不强制先查全盘GMV。相关已有证据足够时补缺项，不重复全查。

**指标关系必须有适用条件：**

- 同一成功支付订单／商品集合、期间、币种和税费口径下：`G = O × A`、`G = Q × P`、`A = U × P`，其中 `U = Q/O`。
- 零分母时派生量为NULL，不能硬套恒等式；数据缺失或关联造成集合不完整时先对账。
- 两套GMV拆解是不同观察角度，不是独立原因，贡献不能相加。
- 同一可追溯会话集合中，若对应订单和金额完整，可使用“会话数×购买会话转化率×每个购买会话订单数×该集合订单客单价”。不能删掉每个购买会话订单数，也不能把按支付月的金额和按会话开始月的转化率直接当成同一恒等式。
- HomeNova已登记的支付商品GMV不因后续退款回写。退款可以解释退款后净收入等其他目标，不能直接解释该口径历史GMV下降。
- 客单价上涨不等于涨价，可能有每单件数或商品组合变化；总会话稳定也不能排除渠道质量／构成变化。

**分支依据真实信号，而非固定下钻路线：**

| 已查信号 | 优先区分的解释／证据 | 结论边界 |
|---|---|---|
| 订单减少，AOV上涨 | 商品件数、每单件数、商品组合、可比SKU价格／折扣 | 不能直接写涨价，也不能忽略销量 |
| 会话总量稳定，购买转化下降 | 渠道／商品转化及构成、适用漏斗事件 | 总量稳定不排除结构变化，不能定位结账页面 |
| 某对象变化贡献突出 | 该对象时段、相关经营事件、对照与反证 | 贡献最大不等于原因已证明 |
| 库存阻断增加 | 对应SKU／时段的可售状态、购买机会与替代选择 | 事件次数不等于失单数，更不直接等于损失GMV |
| 平均每件金额变化 | 同SKU成交金额／折扣、数量权重、新增退出商品 | 平均数变化不能单独证明统一涨跌价 |
| 退款变化 | 原目标是否扣退款、原成交集合和售后观察长度 | 不越过登记的退款政策 |

每个相关的主要解释记录：为什么考虑、需要什么证据、已查结果、支持、反证、状态与下一项最能区分解释的查询。状态至少区分支持、解释力较小、被反驳、未解决、不适用及经核实能力不足。“不支持”与“没查”不同。

数量关系和贡献用确定性计算。首版两因素乘积分解固定采用对称分解：对 `G = O × A`，订单分量为 `(O1-O0) × (A0+A1)/2`，AOV分量为 `(A1-A0) × (O0+O1)/2`，两者合计核对 `G1-G0`。仅在同集合关系成立、分量有效时使用，零分母／缺失值不能强算。这属于算术贡献，不宣称反事实因果损失。不同维度的贡献不能相加，Top N保留正向抵消与“其他”。

### 14.8 让报告可以核对，而不是只看结论措辞

报告的可信度来自可见比较、解释覆盖与证据边界。不能承诺“所有其他原因不存在”，但必须让用户知道哪些方向已经核查、哪些仍可能改变结论。

同一DataQa草稿按以下阅读顺序组织，已有结果直接使用，不新增分析模型：

1. **直接回答与完成程度。** 对原问题给出已核实解释或阶段性诊断，明确本次回答到哪一层。
2. **相关核心指标对比表。** 两期值、绝对／相对变化、单位、范围、实际结果引用。显示恶化、正常、正向抵消项；比率区分百分点和相对变化；月长、未完整期间或成熟度的重要影响同时说明。
3. **指标关系与主要贡献。** 使用适用恒等关系核对总体，解释数量、金额和构成的变化，不将不同集合强行对账。
4. **主要解释核查表。** 每个相关方向列出支持、反证、状态及结论边界。正常项也要有实际数字，不能只写“已排除”。
5. **下钻证据。** 展示与当前结论真正相关的渠道／对象／商品／事件证据，保留抵消项和范围；必要图表与正文共用数据。
6. **未解决问题与建议。** 说明技术失败、能力不足、未查询、口径未对账等区别；经营建议来自已核实问题，未执行或未验证的措施不宣称有效。

报告不能把用户描述解释成心理原因，不能由购买转化率定位具体页面，不能把访问会话改写为人数。正式指标名称、对象、单位和显示换算使用登记／结果元信息；自然语言解释仍由原有最终Reviewer核对，不增加关键词拦截器。

例如，针对本次数据可以显示“会话总量接近持平”的数字，但只能说明总量减少的直接解释较弱；渠道构成恶化仍待查。AOV上涨显示为正向抵消，但不能据此声称所有商品均未降价。这种说明比一句“排除流量／价格因素”更可信。

#### 14.8.1 当前案例的报告形态示意

下表仅使用已独立核对的八月底公开快照数据解释展示方式，**是开发方案示例，不是下次模型的预设答案，不写入运行Skill或少样本提示**。实际实现后仍须经真实工具取得证据和版本。金额为EUR；商品集合按成功支付归期，会话指标另按会话开始归期，不能直接拼成同集合因果恒等式。

| 指标 | 2026年6月 | 2026年7月 | 变化 | 能说明什么 |
|---|---:|---:|---:|---|
| 成功支付商品GMV | 39,200.44 | 30,905.83 | -21.16% | 核实用户关注的总体变化 |
| 支付订单数 | 946 | 687 | -27.38% | 成交订单规模恶化 |
| 支付商品件数 | 1,331 | 917 | -31.10% | 商品销量也下降，不能用订单数代替后省略 |
| 商品客单价 | 41.44 | 44.99 | +8.56% | 对GMV下降有正向抵消，不代表所有商品涨价 |
| 每单件数 | 1.4070 | 1.3348 | -5.13% | 每单数量构成发生变化 |
| 平均每件实付金额 | 29.45 | 33.70 | +14.43% | 需区分商品组合、同SKU成交价与折扣 |
| 有效会话数 | 24,932 | 24,704 | -0.91% | 总量接近稳定，仍不能排除渠道构成变化 |
| 会话购买转化率 | 3.79% | 2.78% | -1.01个百分点 | 整体购买转化变差，尚不能定位具体漏斗环节 |

变化按完整精度计算，显示值四舍五入；6月30天、7月31天，月总额保留原问题口径，另核对日均／完整期间的可比性，不能只把“总会话稳定”扩大为“每天流量稳定”。

配套解释覆盖表示意：

| 待解释方向 | 本次证据 | 可以得出的判断 | 尚不能得出的判断 |
|---|---|---|---|
| 整体每单金额下降 | AOV反而上涨 | 整体AOV下降这一解释被反驳，金额提升在抵消下降 | 各SKU均未降价 |
| 总会话规模减少 | 总会话微降 | 月度总规模的下降幅度较小 | 渠道质量／构成没有问题 |
| 商品价格或组合变化 | 平均每件金额上涨、每单件数下降 | 存在进一步区分价格和组合的必要 | 已证明商品涨价导致某项变化 |
| 某一成交环节受阻 | 必要漏斗查询失败 | 本次未查清，应继续取证或保留核心缺口 | 已确认是结账页面问题 |
| 退款直接回写历史GMV | 登记定义明确不回写 | 此直接扣减路径不适用于当前GMV口径 | 退款与未来经营行为完全无关 |

用户最终应看见：已核实的数量与金额变化、正向抵消、整体与结构的区别、哪些解释经过比较，以及哪些原因还没获得证据。报告不能把这张示意表本身当成“原因已完整查明”。

### 14.9 完成条件与最终审核

正常路径仍只有一次独立最终审核。Reviewer针对原问题ID、核心指标表、解释覆盖记录和实际证据，对每个核心缺口明确处置：证据已回答、有依据不适用、仍受阻或仍需取证。不能仅返回空缺口数组关闭已有问题。

完成需同时满足：

- 用户范围、比较前提、核心相关指标已核实；适用关系、总体及分组能核对。
- 对用户实际原因问题达到足以回答的解释层级，不只是重复“某个指标下降”。结论强度区分事实、算术驱动、分组贡献、关联和有机制证据的解释。
- 重要竞争解释已有适当核查／反证，或有证据说明不适用；报告公开它们的核查程度。
- 当前影响核心答案的必要问题已经处理。查询失败不等于问题已经回答，不能改称经营建议来消除缺口。
- 没有会推翻主要结论的未决口径／集合错误；证据引用有效且报告数字、单位、图表一致。

不要求发现唯一原因或穷尽所有理论可能。若存在必要、可行的补查且预算允许，Controller继续；没有预算或可行路径时交付partial并列明已知／未知；缺用户条件时waiting_clarification；没有可用交付时failed。无变化同稿不重复审核，审核后不再自由改写。

**本次任务的处理原则：** 已确认支付结果及购买转化变化可以交付，但SQL失败而仍开放的漏斗／来源等核心问题没有自动解决，不能把“已找到一个算术驱动”升级为“业务原因完整查明”。

## 15. 调查记录协议：先兼容转换，再检查实际依赖

2026-10-29补充，响应实际任务中“数据已查到、记录编号格式却导致整轮停止”的问题。适用于执行协议3，不增加过程审核，不改变SQL生成次数、业务取证轮数、权限或预算规则。

1. **模型格式与代码同源。** ReAct输入提供后端类型定义生成的进度Schema；省略或null表示该部分未更新。只输出变化项，不必每轮抄写全部进度。提示词说明事实F、结果R、假设H的区别，但不把每一种可转换写法都变成失败。
2. **引用先解析。** 从当前用户、任务、数据源和快照已验证的结果目录出发，将已登记或同轮新增事实的明确引用链展开到真实结果，持久化真实R引用并保留F引用关系。唯一匹配的结果简写可展开；不能按数字尾号猜F对应哪个R。此转换只确认来源身份，不认证文字、数值或因果解释正确。
3. **逐条隔离记录问题。** 无效可选笔记不抹去同轮其他有效更新，也不阻止有合法参数与依赖的独立查询。原核心问题继续保留；新增核心问题的关闭或引用有误时，能识别的问题保留为open，不能因丢弃坏记录而从最终审核消失。
4. **动作依赖单独检查。** 当前事实更新被拒绝时，当轮依赖不能回退到同名旧事实；未知、失效、循环、歧义、无真实来源、假设冒充证据或跨范围引用均不能用于执行。存在实际依赖就必须解析成功，不能删除依赖来绕过检查。单结果动作若对应多个结果，仍要求明确选择。
5. **反馈服务于正常流程。** 记录确定性转换、被拒绝条目、字段路径和错误引用；进入下一轮正常决策及收尾上下文。可恢复的笔记格式问题不单独触发付费模型修复，也不占react_protocol额外修复额度。真正无法执行的动作继续服从原受控错误分支。

验收先独立重放真实失败任务的三个原始决策，验证进入下一步动作派发且无协议修复扣次；再覆盖无效引用、跨范围、同名失败更新、核心问题保留和独立查询执行。回放与受控测试不计为真实模型业务成功，不为此次修复新增付费试跑。实际验证及部署结果另存修复报告，不改写历史失败记录。
