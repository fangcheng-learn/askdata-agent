# 库存风险筛查

## 适用与边界

适用于“当前哪些商品不可售”“过去发生过多久缺货”“已知到货能否覆盖某段需求”等问题。简单库存查数验证后即可回答；仅在问题需要时延伸到缺货区间、采购或需求情景，不强制长计划或报告。

不做实时 listing 检查、外部页面访问、补货下单、调拨或其他业务操作。不凭库存事实给出精确失单、损失金额或唯一经营原因；不提供未经定义的安全库存等级或保证未来安全。

## 必要输入与缺失处理

运行层须实际提供下列上下文；Markdown 路径和引用不会自动加载文件：

- 用户问题、SKU/仓库范围、观察时点或历史区间，以及仍适用的已确认条件。只有会实质改变答案的业务歧义才询问用户，不逐次确认下钻。
- 当前绑定的数据源及快照标识；同一快照的 `dataset_metadata.json`、`capabilities.json`，以及 `metrics.json`、`schema.json`、`glossary.json` 中相关完整条目（含依赖、粒度、关联和重复风险）。
- 可用只读查询能力及真实已有结果：结果 ID、来源 SQL/查询契约、筛选、时间范围、单位、行数、是否截断及覆盖情况。来源和快照不匹配的旧结果不得复用。
- 如需未来风险判断：用户明确提供或合法配置的评估期限、安全库存/服务水平规则、需求估计方法与窗口、采购到货和验收假设；不存在默认值。

缺快照、语义或结果时，提出需要运行层补充的具体内容，不猜表、字段或库存规则。区分“尚未查询”“查询失败/结果不完整”“公开数据没有必要字段或定义”；不能把前两者称为数据不存在。缺风险参数仍可报告库存与采购事实，列出待确认条件。

## 公共口径

- 以当前公开语义为准，不凭指标名称重定义。相对时间按绑定快照的场景日期和时区解释，遵循其观察截点及可知时间；不用机器日期，也不借另一快照补未来。尾窗末快照不代表有持续到该日期的新交易或需求。
- 在当前公开口径下，在库是累计 `on_hand_delta`，预占是累计 `reserved_delta`，可售是二者之差；按 SKU×仓库及 `occurred_at, event_seq` 重建。销售单位不因 `pack_units` 自动乘成物理件数，库存余额不可跨日相加；支付不再次扣库。
- 原计划收货、实际到仓、实际验收上架分别列示；在途或已到仓未验收不算可售。资金退款完成不等于退货验收；仅实际验收可再售并产生入库事实才恢复销售库存。支付、发货、退款完成、退货验收的事件时间不得互换。
- SQL 执行成功不等于口径正确；检查关联基数、去重、时间和完整性。截断明细或 Top N 不能作全集；应请求完整汇总、剩余汇总或必要补查。

## 最小分析步骤与证据

按问题取用以下步骤，已有合格证据可复用。后续方向由缺口和结果决定，不要求每次全跑。

| 步骤 | 必须获得的证据 | 改变方向的条件 |
|---|---|---|
| 1. 固定范围与目的 | 快照、场景日期/时区、SKU/仓库、时点/区间；确认问当前事实还是未来风险 | 范围不清且影响结果时澄清；只问当前余额时无需需求预测 |
| 2. 核验当前余额 | 指标定义及截至时点完整事件/等价可核验汇总，分别给在库、预占、可售；保留期初与历史事件，不只累计所选区间内的增减 | 余额不一致、负值或事件缺失时先建议修复/补查；不能直接解释成正常缺货或强行归零 |
| 3. 按需回看缺货 | 重建可售为零的实际区间，带入区间前状态，按当地经营日切分；列连续区间和累计时长，说明观察边界 | 当前有货不能否定历史缺货；无区间起点状态只能部分回答。若问影响，可补不可售访问/库存阻断事件，其数量不等于失单或潜在需求 |
| 4. 按需核对采购 | 按 `procurement_id` 批次核对原计划时间/量、当前可知状态、到仓与验收时间/量，以及对应库存 receipt；`purchase_reference` 非唯一 | 计划时间已过但无实际证据，只报未观察到到仓/验收及计划偏差；不得假定已经入库。已计入余额的 receipt 不得再次作为未来供应相加 |
| 5. 有参数才判断未来 | 期限、需求方法/窗口、可售起点、计划可用时间/量、阈值来源和假设；列可复算的供需情景 | 缺阈值或需求定义时停在事实与条件。历史销量受缺货和覆盖限制，不能直接当未受约束需求；情景中的计划到货不能写成已发生事实 |

每个关键数值保留对应结果 ID、指标/字段、时间范围和计算依据。跨表前先按各自事实粒度汇总，避免采购、库存、订单或行为事件多对多放大。

## 何时充分、何时部分回答

- 当前库存问题：指定范围内余额与单位、时点、来源及完整性已核验即可结束。历史缺货问题还需区间起点状态、完整事件顺序及观察终点；不能用某天零销量代替缺货证据。
- 风险判断：必须有可追溯的阈值/需求方法和明确期限，才可按该规则给条件性判断；即使未触发规则，也只能说“在所述条件下未触发”，不能宣称确定安全。
- 必要数据未取得、区间覆盖不全、采购终态未知或参数缺失时，返回已核验事实与未解决问题。缺参数不妨碍完成事实筛查，但“能撑多久/会否缺货”只能部分回答；查询失败不证明没有缺货或没有采购。

## 输出

按问题复杂度输出简答或小表：范围/快照/截至时点；在库、预占、可售事实；按需给历史缺货和采购计划与实际；证据引用；若有情景则单列方法、参数来源、假设和条件性结果；最后说明限制、尚未查询项、数据不支持项及待确认问题。可建议补查、修复、调整评估条件或结束。

本 Skill 只定义分析与建议；实际调度、状态保存、权限校验和重试限制由 Harness 实现，不在这里约定自动执行。

## 简短示例

- “现在有哪些 SKU 没库存？”按场景时点核验在库、预占和可售，列可售为零的商品；无需求参数也能回答当前不可售事实，不附未来风险等级。
- “这批货下周到，能避免再次断货吗？”先核验公开数据中的采购批次、计划和实际验收；缺需求口径或验收可用假设时报告缺货历史与采购事实，列所缺条件。条件具备后给供需情景，不承诺计划到货或未来不断货。
